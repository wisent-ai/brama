Runbook¶

Something at the gateway looks wrong — which command do you run first, and what does its answer mean? Each entry starts from the symptom, quotes the exact sentence the product uses (every string below exists in source or was captured from a running 0.2.38 gateway), and names the repair. The error vocabulary itself is in errors.

brama serve refuses to start¶

The sentence, verbatim (exit 1):

Server error: BRAMA_MODEL_ALIASES is required and is assembled by
scripts/start-with-skarbiec.sh from the sealed policy directory. Starting the
binary directly cannot obtain it: launch the gateway through that script, or
export the variable yourself. Restarting an unlaunched process will not
repair this.

The refusal names its own repair: managed configuration is generated by the launcher, and restarting the same bare invocation cannot change the answer. Start through scripts/start-with-skarbiec.sh; a standalone desktop deployment instead passes --local-credentials-stdin (configuration). Other startup refusals in the same class — duplicate client tokens, malformed identities, an alias route with * or stray whitespace — also fail the process before it binds; the log names the offending entry.

/health is ok but nothing works¶

That is /health doing its job, not a contradiction: its body says "dependencies": "not_probed", and it answers ok from a gateway whose every credential redemption is being refused. The only readiness evidence is /readyz (architecture). Point deploy checks and uptime monitors at /readyz; treat a monitor on /health as a monitor of the process, nothing more.

/readyz answers 503¶

reason is one of five sentences (src/core/server.rs:2343-2355), each naming a different repair:

reason Meaning Check
no provider capability is configured zero direct providers — the gateway can route nothing on its own account launcher policy: required_provider_capabilities, BRAMA_PROVIDER_CAPABILITY_IDS
a configured provider credential could not be obtained; the authorization chain is broken, not busy a capability or read grant refused just now denied[] names the providers; check broker socket, workload registry, proof key (concepts/capability)
an active subscription's credential did not redeem just now, so the next request that needs it will be refused whatever the catalogue lists a subscription is listed but its credential does not redeem unredeemable[], then brama subscriptions list for the refusal sentence
the vault holds a subscription account whose item carries no agent tag: it is unroutable, and no subscription listing can report it an account lost its brama:agent: tag; the credential still works and nothing can route to it unroutable_accounts[] names item and coordinate; restore the tag in the vault
every credential was obtained, and at least one active subscription contributes no model: it cannot be routed to a redeemable account whose provider offers it no discoverable model unroutable[]; check provider model discovery and the account's plan

Waiting repairs none of these — every 503 here is an authorization or inventory statement, not load.

A request answers 503 credential_unauthorized¶

The dispatch sentence behind it is usually direct '<provider>' credential is unavailable — no capability, read grant, or standalone credential could produce a secret for that provider at final use. It is retryable: false on purpose: waiting does not reach an authorization that does not match. Check, in order: /readyz (denied[]), the launcher's provisioned trust material (bin/provision-skarbiec-trust was run once on this installation), and whether the alias's route names a provider this host was ever granted (alias_provider_capability_absent in the log at startup: "no provider capability was issued for this route; the alias will not serve").

A request answers 429 subscription_unavailable¶

The dispatch sentences, from narrowest to widest (concepts/entitlement):

  • no active '<provider>' credential for agent — the signed agent owns no eligible credential for the provider the route names.
  • no active stateless provider models for signed agent — a selector found no candidate at all.
  • no working subscription model for signed agent — the selector walked its whole bounded candidate list; the body's attempts counts the provider calls actually paid for.
  • all bounded '<provider>' credentials unavailable for agent — every bounded credential was tried or is inside a recorded block.

First command: brama subscriptions list. 0 of 0 subscription credentials are live is the whole diagnosis — sign an account in. Rows present but refused carry last_redeem_error in the words of whatever refused (credential cause first, then a block still in force, then the newest failed check; a lapsed block is deliberately not reported).

A subscription reads burnt¶

burnt covers both recorded dead states — a grant the provider disowned and a subscription somebody retired — and last_redeem_error says which. A definitive provider refusal (invalid_grant, invalid_token, revoked, unauthorized_client, or an unexplained 401/403) is recorded as credential.state: needs_reauthorization with the provider's own sentence as cause, and the credential is left alone until a sign-in replaces it — the refresh timer will not resurrect it, and a 30-minute block keeps the dispatcher off it. Repair: sign the subscription in again (Desktop or a donation), then:

$ brama subscription refresh <provider> --reason "<why>"

Exit 0 with result: refreshed is the proof; result: failed quotes each refusal in the provider's own words. A retirement outranks everything: a retired subscription is never refreshed.

subscription refresh fails with attempted: 0¶

detail: no usable `<provider>` subscription is in this deployment's pool, so
no credential source is configured to refresh: one has to be signed in and
stored in the vault before this command has anything to act on

Not a fault in the refresher — the pool is empty for that provider. The same sentence answers a provider with no OAuth path. Sign an account in first; the walkthrough shows the full sequence (walkthrough-subscriptions).

An account vanished from every listing but keeps paying¶

The tag-loss case: discovery finds an account by its brama:agent: tag, so an item that loses it stops existing for every caller and every screen while its credential stays valid. Nothing that lists subscriptions can say so — the listing is the thing that lost it. The one reporter is /readyz: unroutable_accounts[] names the item id, provider, and coordinate (items stripped bare are recognised by the provider:<provider>:<id> coordinate alone). Repair in the vault: restore brama:subscription, brama:agent:<agent>, brama:provider:<provider>, brama:id:<id>.

Requests from another machine answer 426¶

{"error":{"code":"secure_transport_required",
 "message":"HTTPS is required except for direct loopback requests", ...}}

The transport guard accepts loopback, the gateway's own bound address, peers in BRAMA_ENCRYPTED_PEER_IPS, and proxies in BRAMA_TRUSTED_PROXY_IPS whose forwarded headers state https — nothing else, and forwarded headers from an unlisted peer are never trusted (a forged X-Forwarded-Proto: https changes nothing; captured). Repair: front the gateway with the approved TLS terminator and list that terminator's peer IP, or call over the mesh hop that is already encrypted.

A provider refuses its own credential¶

A direct route whose provider answers 401 returns 502 provider_failure with the provider's sentence behind the kind prefix:

{"error":{"attempts":1,"code":"provider_failure",
 "message":"provider_authentication: Incorrect API key provided: ...", ...}}

Distinguish it from 503 credential_unauthorized: the 502 means Skarbiec (or the standalone map) produced a credential and the provider rejected it — the repair is at the provider account, not the authorization chain. A provider 429 surfaces as 429 provider_rate_limited with retryable: true; a recorded block (default 15 minutes, provider-stated resets capped at 7 days) then keeps ordering away from that account.

A route update is refused¶

PUT /v1/admin/routes refusals, verbatim:

  • runtime route registry is not configured (409) — no BRAMA_INFERENCE_ROUTES_FILE is in effect; configure it (the launcher seeds one) before editing routes at runtime.
  • unknown route alias / route chain is unsupported, duplicated, or unavailable (400) — the alias or chain fails validation; the routes file guards in concepts/alias list the file-level sentences (inference routes must be a regular non-symlink file, inference routes must not be accessible by group or other, inference fallback route '<alias>' has no primary destination, inference route '<alias>' repeats destination '<destination>', inference deployment '<name>' has no safe local or Tailscale endpoint).

The file is re-read per request, so a repaired file needs no restart.

The ledger looks wrong, not the pool¶

An empty limits array in a listing is one of four states told apart by the newest check — a refused credential, a subscription nothing has used, a provider that publishes no plan state, or windows that aged out (BRAMA_PLAN_USAGE_RETENTION_SECS, default 86400). Only the third may be read as "no plan window"; none of them is a zero. A reading marked stale: true is a served last-good value whose provider report has been failing — information, not health (concepts/subscription).

Providers¶

One page per provider, written against src/providers/adapter.rs — the descriptor table in the source is the truth and these pages follow it. What a provider is at all, and what it deliberately is not, is defined once in concepts/provider; this catalog is about the part that differs per provider: how we authenticate to each one.

Three ways in¶

Subscriptions (OAuth). claude-code, codex and kimi are agent-owned provider accounts. The credential is an OAuth grant — an access token, a rotating refresh token, and an expiry — minted by a real browser sign-in that Weles drives on its own host and writes into the Skarbiec vault at provider:<provider>:<subscription>. The gateway refreshes the grant ahead of expiry against the provider's own token endpoint and never opens a browser itself; a grant the provider disowns waits for the next sign-in (subscription, each provider's page for the exact token shape).

Deployment API keys. Every other remote provider is paid by the deployment's own long-lived API key, stored once in the vault and redeemed at final use through a capability. There is no login flow, no refresh and no invented expiry — the key works until the provider revokes it or an operator replaces it.

The routes file. local-openai is the deployment's own inference: its endpoint resolves per request through the routes file and only loopback or Tailscale IPv4 endpoints are accepted (alias).

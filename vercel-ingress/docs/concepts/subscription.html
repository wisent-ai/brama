Subscription¶

One provider account delegated to one agent: a Skarbiec vault item whose credential Brama redeems at final use and whose plan state Brama reads from the provider's own reports. Who may spend it is the entitlement model; this page is the object itself — discovery, states, the ledger, and the credential lifecycle.

Shape and discovery¶

A subscription is a vault item tagged brama:subscription and brama:agent:<agent>, carrying its provider in brama:provider:<provider> and its subscription id in brama:id:<id>. Brama discovers those tags and Desktop consumes the returned accounts and errors; it does not keep a second list. Vault item ids stay opaque. The credential coordinate is provider:<provider>:<subscription> (src/gateway/broker.rs).

Discovery shells the local entitlements router's list (binary from ENTITLEMENTS_ROUTER_BIN, default entitlements-router); successful listings are cached per agent for 60 seconds. User-facing discovery preserves process errors, exit status and stderr, malformed output and timeouts. A trusted startup catalog may support routing, but never hides a failed live lookup in the operator's report.

An item that loses its brama:agent: tag keeps a working credential and stops existing for every listing — the one failure the deployment had no way to see, which is why /readyz reports such accounts explicitly as unroutable_accounts (metadata only, recognised by tags or by the coordinate an untagged item lives at).

States¶

brama subscriptions and GET /v1/subscription-pool report one of four states per row (src/subscription_dispatch/pool.rs):

State Meaning
live credential recorded active, expiry absent (API key) or in the future
expired credential active but its stated expiry has passed
burnt the provider disowned the grant (needs_reauthorization) or somebody retired it; the pool serves neither, and last_redeem_error says which
unknown a subscription whose grant nothing has ever looked at — deliberately not the same statement as a working one

last_redeem_error reports the refusal standing in the way, in the words of whatever refused, with fixed precedence: the credential's own cause first (set only while the grant is refused; only a sign-in clears it), then a block still in force, then the newest failed check. A lapsed block is deliberately not reported.

The usage ledger¶

BRAMA_SUBSCRIPTION_USAGE_FILE (default ~/.config/brama/subscription-usage.json, owner-readable, written atomically) holds per-subscription state: measured counters, the newest plan reading per window with its instant and source, any rate-limit block, the credential state, completion checks and the independent newest free-usage attempt. It is not a cache. Older ledgers remain readable; malformed or unreadable history is reported with its path and actual reason rather than silently replaced with an empty file. Failed writes remain visible together with last-good in-memory readings.

Plan windows come from each provider's own free usage report (provider lists the three supported endpoints). Other providers are reported as unsupported by this free-report path with the current credential, not as successfully queried billing APIs. Observed traffic counters remain available. Background reads obey BRAMA_PLAN_USAGE_TTL_SECS (default 300), jittered ±25% derived from the subscription id so accounts stay decorrelated across restarts, and single-flighted per subscription; the sweep runs every BRAMA_PLAN_USAGE_SWEEP_SECS (default 60, 0 disables). A failed read never blanks a row: the last good reading is served with stale: true and dropped only past BRAMA_PLAN_USAGE_RETENTION_SECS (default 86400).

brama subscriptions --refresh-usage, Brama Desktop's Refresh usage and POST /v1/plan-usage are one capability: they explicitly request new reports through that same bounded operation, and the route narrows its answer to the accounts the caller proved it owns. Neither starts a sign-in nor sends a model request. Concurrent attempts for one subscription cannot silently skip their result. A failed attempt, an elapsed reset or an aged retained window marks the reading stale immediately; one fresh window does not make older windows current.

In listings, usage_source names which statement the newest window is — provider (the provider's report, no quota), traffic (response headers), or probe (the operator's on-demand check). usage_check holds the latest free-report attempt's time, success and detail independently of completion checks. An empty limits array can mean an unread account, a failed read, expired history or an unsupported report; none means zero usage. Missing or malformed metrics from a publishing provider are errors, not unsupported reports.

Every list and refresh includes ok, observed_at_ms and errors. A partial report retains successful accounts and returns ok: false, including on HTTP 200. CLI exits non-zero; Desktop shows each failed operation beside retained stale data. If Brama itself cannot answer, the client reports the connection or decoding failure.

Blocks¶

A rate-limited provider answer records a block: 15 minutes by default, capped at 7 days when the provider states a longer reset, and 30 minutes for a credential awaiting re-authorization (src/subscription_dispatch/usage.rs). A blocked credential is skipped by ordering, refused by the probe (409), and the block stands until its own expiry.

Credential lifecycle¶

OAuth subscription credentials (claude-code, codex, kimi — token endpoints in src/gateway/oauth_refresh.rs) are refreshed ahead of expiry: every BRAMA_CREDENTIAL_REFRESH_INTERVAL_SECS (default 60, 0 disables) the gateway refreshes every active credential expiring within BRAMA_CREDENTIAL_REFRESH_SKEW_SECS (default 300), single-flighted per subscription. Refreshing costs no plan quota. API keys have no refresh path and no invented expiry.

A provider refusal such as invalid_grant, invalid_token, revoked or HTTP 401/403 records needs_reauthorization. A stored OAuth document with no refresh token also requires authentication; waiting cannot add a missing token. Transport failures remain separate from provider refusals.

The gateway reads the live subscription inventory from Skarbiec. For a subscription requiring authentication it asks Weles to resolve the same subscription id against Skarbiec, then execute the provider OAuth flow on its Stado-selected host. Account identity, login method and login material come from Skarbiec; Weles has no independently maintained account catalogue. An optional existing login reference may identify the item, but no additional brama:login: tag is required to make an account eligible.

Weles performs OAuth without launching provider CLIs or copying their local sessions. The captured grant is persisted for the same subscription and Brama checks the persisted grant through its refresh path. Credential writes preserve the item's context and other fields, rather than replacing its account identity.

automatic_sign_in reports not_observed, failed, succeeded or not_applicable. Its last_attempt retains the actual failed operation, HTTP status, Weles run id, account-data revision and returned detail. No authentication failure is inferred from an inventory tag. A non-retryable provider challenge is not repeated against unchanged account data; changed Skarbiec data is resolved again automatically. Readiness exposes these same observations under automatic_sign_in.blocked; unknown host placement is null, not a claim that the host is correct. See the credentials runbook.

Donation and retirement¶

POST /v1/subscription-pool (and the account/admin variants) banks a credential onto the coordinate the operator's routes table already names for that subscription. A donation is refused unless the document reduces to a bearer — the same reduction the request path applies — so a non-credential document can never overwrite the one copy of a working account. The plaintext crosses only the request body and the entitlements-router stdin pipe; the overlay file (BRAMA_DONATED_SUBSCRIPTIONS_FILE, default /tmp/brama-skarbiec/donated-subscriptions.json, atomic 0600 rewrite) holds metadata only.

DELETE retires: an append-only journal record ({"kind":"retire","id", "at"} in BRAMA_STATE_DIR/journal.jsonl) that outranks whatever the last refresh concluded, never a vault deletion. A retired subscription is never refreshed, because rotating its grant would put back what somebody removed.

Not to be confused with¶

  • A capability. The capability is the deployment's direct spend; a subscription is an agent's delegated account.
  • An entitlement. Owning the item is not the decision about who may spend it on which request — that is entitlement.

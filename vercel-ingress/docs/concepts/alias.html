Alias¶

What the model names callers use actually mean. An alias is a deployment-owned name that resolves to a canonical provider/model route. Callers ship against aliases so routes, providers, and subscription-backed selection can change without a client release; an alias never unlocks a credential its caller does not own.

The model-name vocabulary¶

A request's model field must be one of exactly four things:

  1. an alias the deployment declares (wisent-backend, smol, …);
  2. the delegation alias best;
  3. a canonical provider/model route (openai/gpt-4o-mini);
  4. a selector (any, any-vision-capable, task:<task-name>) — signed agents only, see entitlement.

Nothing else is guessed. A bare vendor model name is refused before any provider is considered:

$ model="gpt-4o" → 400
{"error":{"code":"invalid_request","message":"model must be a canonical
 provider/model route or a supported selector", ...}}

Declared aliases¶

BRAMA_MODEL_ALIASES (assembled by the launcher from the sealed policy document, extended per request by the routes file) maps alias names to canonical routes. Seven aliases are required in managed deployments because callers ship against them:

Alias Shape promise
wisent-backend chat — the Wisent App backend's alias, spelled as the client's name and nothing more. The shape is the endpoint the caller posts to, and the one route behind the alias is the routes entry in the route table; neither is spelled into the name
wisent-backend/evaluation chat
wisent-backend/embeddings embeddings only — never handed a chat model
wisent-backend/moderation moderation only
weles chat — the Weles workload's own alias, spelled as the client's name; which model answers it is the route table's decision
best delegation to subscription dispatch

Any further name is the operator's to invent and is accepted on the general-purpose chat shape without a gateway release. A route containing * or stray whitespace fails startup. A route naming a provider whose capability was never issued on this host does not fail startup: the gateway starts, serves the aliases that are serviceable, and logs alias_provider_capability_absent — "no provider capability was issued for this route; the alias will not serve" (src/core/server.rs).

An alias that cannot serve says so¶

A declared alias is never silently dropped. The gateway judges every alias it knows into one of four states, and every surface reports the same word:

statemeaningrepair
servingat least one declared route names a provider this gateway holds a credential for, or delegates to bestnone
no_routethe alias is known — required by the contract or named by a caller's allowlist — but no route is declared for itdeclare a route with PUT /v1/admin/routes or in the launcher's model_aliases policy
capability_absentevery declared route names a provider whose capability was never issued on this hostissue the provider capability, or point the alias at a route the host can reach, such as best
routes_file_invalidthe route registry file exists and cannot be read, so nothing in it servesrepair the file named by BRAMA_INFERENCE_ROUTES_FILE

Where the verdict is read:

  • GET /v1/models lists a declared alias the caller may use even when it cannot serve, as available: false with unavailable_reason carrying the sentence above. A caller that checks the catalog before calling — Jeden does — therefore reports model `weles` is unavailable: alias `weles` routes to … but this gateway holds no provider credential for … instead of not in the Brama catalog.
  • A completion request naming a declared alias that cannot serve is refused with 503, code alias_unserviceable, the same sentence as message, and details.state, details.route. It is not refused as a malformed model name. An alias this gateway does not declare at all is 404, and its details carry the same state and route pair.
  • GET /v1/aliases is the operator's view: every alias with state, route, reason, whether the contract requires it, and whether the presenting bearer may use it.
  • brama aliases prints the same table from an operator shell and names the route registry file it read; --strict exits non-zero when any alias cannot serve.
  • Brama Desktop's Routing screen carries a Gateway column and a Not serving facet, and its inspector shows the reason verbatim; an alias the gateway requires but has no route for appears there with an Add route action even though the registry has no row for it.

In standalone desktop mode an absent BRAMA_MODEL_ALIASES means {}; in managed mode a bare brama serve fails closed with the exact sentence in the runbook.

best is delegation¶

best (and any alias whose route delegates to best) resolves through subscription dispatch, where the caller's signed HMAC identity selects the subscription that pays. Brama deliberately holds no direct credential for it. A destination naming best inside the routes file passes through untouched rather than being resolved as a local deployment (src/core/inference_routes.rs).

Dynamic routes: the routes file¶

is reloaded per request and its routes extend the launch aliases. The document has exactly three known top-level fields — schema_version (the number one), deployments, and routes, which maps each alias to its single destination:

{
  "deployments": [
    {"name": "qwen3-8b", "adapters": [{"name": "chat"}],
     "endpoint": {"host": "127.0.0.1", "port": 8000}}
  ],
  "routes":    {"wisent-backend": "openai/gpt-4o-mini"}
}

Guards, each failing closed with its own sentence (src/core/inference_routes.rs):

  • inference routes must be a regular non-symlink file
  • inference routes must be owned by the Brama user
  • inference routes must not be accessible by group or other (mode 0o077 bits must be clear)
  • an unknown top-level field: the deserializer refuses it by name and the whole document is rejected
  • a repeated destination: inference route '<alias>' repeats destination '<destination>'
  • a bare deployment name resolves to local-openai/<name> only when its endpoint host is loopback or Tailscale IPv4 (100.64.0.0/10) and its port is nonzero; otherwise inference deployment '<name>' has no safe local or Tailscale endpoint.

PUT /v1/admin/routes ({"alias", "primary"}) persists operator route changes into the same file atomically (staging file, 0600, validate, rename), and brama routes migrate moves a registry file written before this contract onto the shape above in one idempotent operation. Without a configured routes file the update is refused:

409 {"error":{"code":"state_conflict",
     "message":"runtime route registry is not configured", ...}}

Lifecycle¶

Launch aliases live for the process lifetime; restart after policy changes. Routes-file aliases change whenever the file does — the snapshot is re-read per request, so an update is visible to the next request without a restart.

Not to be confused with¶

  • A selector. any, any-vision-capable, and task:<name> are not names for one route; they rank candidates per caller identity (entitlement).
  • A canonical route. provider/model names one provider directly and is paid by the deployment's own capability, never by a subscription.

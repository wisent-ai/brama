Brama integration contracts

Integration contracts¶

An integration is a boundary Brama depends on but does not own: a model provider's HTTP API, the public models.dev catalog, the Skarbiec capability broker, the entitlements router, GitHub Releases together with the host service manager, and Weles reauthentication. Brama owns the normalized contract at that boundary and nothing behind it.

Integrations extend the stable core in CORE.md. They do not redefine client identity, subscription ownership, routing limits, state authority, or public error semantics.

This index states what every integration is, in one row each, and links the four pages that carry the contracts.

Routing is not an integration¶

Which provider serves an alias is Brama's own decision, recorded in the route registry document. An alias names exactly one destination route. When that route refuses a request, the refusal is what the caller receives: no second route is attempted, and the request deadline is the deadline of that one attempt.

The registry document carries three known top-level fields — the schema version, deployments and routes — and the schema version is the number one. routes maps an alias to its single destination. An unknown top-level field is refused by the deserializer, so a document carrying anything else is rejected whole. An operator moves an existing file to this shape with brama routes migrate, which keeps only the known fields, validates the result, commits it with the same atomic owner-only replacement every other registry write uses, and prints the document. Running it twice changes nothing the second time.

The alias surfaces are PUT and DELETE /v1/admin/routes, GET /v1/aliases and brama aliases. A declared alias that cannot serve answers 503 alias_unserviceable, carrying its state and its route in details; see Errors.

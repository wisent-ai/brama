Brama CLI command reference

brama subscription¶

Enter the command group that reads the subscription pool and acts on one provider’s subscription credentials.

Invocation¶

brama subscription <COMMAND>

A subcommand is required. This group has no options and performs no mutation by itself.

Commands¶

  • brama subscription list [--json] [--refresh-usage] [--gateway <ORIGIN> | --gateway-consumer <NAME>] [--bearer-role <ROLE>] [--apply] — report the pool: every member, its state, its usage windows and its failure; --apply banks or retires one member from a JSON document on stdin.
  • brama subscription discover [--gateway <ORIGIN> | --gateway-consumer <NAME>] [--bearer-role <ROLE>] [--json] — discover account identities without taking a harness's grant, then schedule independent sign-in.
  • brama subscription reset <PROVIDER> --member <ID> --reason <REASON> [--gateway <ORIGIN> | --gateway-consumer <NAME>] [--bearer-role <ROLE>] [--json] — use one eligible saved reset belonging to the selected member.
  • brama subscription refresh <PROVIDER> --reason <REASON> [--json] — refresh one provider’s grants now.
  • brama subscription sign-in <PROVIDER> --by weles|hand --reason <REASON> [--subscription-id <ID>] [--login-item <LOGIN_ITEM>] [--gateway <ORIGIN> | --gateway-consumer <NAME>] [--bearer-role <ROLE>] [--json] — sign one account in and prove it, through an exact Weles sign-in row or by hand in your own browser with the code pasted on stdin; a provider without a manual flow is refused by name.
  • brama subscription authenticator list [--provider <PROVIDER>] [--json] — list which accounts need a second factor to be signed in and which hold the secret that answers one.
  • brama subscription authenticator enrol <PROVIDER> --subscription-id <ID> --reason <REASON> [--login-item <LOGIN_ITEM>] [--json] — enrol an authenticator for the login behind one subscription and confirm the seed landed, so no later sign-in needs a person.
  • brama subscription disown --subscription-id <ID> --reason <REASON> [--gateway <ORIGIN> | --gateway-consumer <NAME>] [--bearer-role <ROLE>] — give one pool member back: the gateway retires it and forgets its credential, and any machine that signed that account in keeps its own session.
  • brama subscription acquire <PROVIDER> --reason <REASON> [--gateway <ORIGIN> | --gateway-consumer <NAME>] [--bearer-role <ROLE>] [--json] — buy one new account when every pool account has spent its plan and the pool holds fewer accounts than the operator allows.
  • brama subscription hand-over <PROVIDER> --harness omp [--json] — sign every pool account a harness on this machine lacks into it through the harness's own login.
  • brama subscription lease take <PROVIDER> --session-id <ID> --holder <PROGRAM> (--gateway <ORIGIN> | --gateway-consumer <NAME>) [--bearer-role <ROLE>] [--json], lease release, lease list — which live session runs on which subscription: the gateway's lease register, the operator's limit of sessions per subscription, and the acquisition a full pool starts.

Discover accounts without sharing grants

brama subscription discover --gateway-consumer <consumer> --bearer-role <console bearer role> --json

Run discovery where your coding harness holds its accounts. Brama reads the public account inventory and usage report, not the harness's credential store. The serving gateway also reads synchronized purchase receipts through Skrzynka. The report identifies each account's provider, address, reported plan, source and observation time. A failed source remains in errors; it is not an empty account list.

Supported local sources are omp usage accounts --json, omp usage --json and Claude Code's claude auth status. Claude Code contributes the email and reported subscription type only when its public status identifies a signed-in claude.ai account. API-key and third-party authentication are not converted into subscription accounts. An uninstalled harness is not a required dependency; an installed harness that fails or reports an incomplete identity retains its actual refusal. Brama never reads either harness's credential files.

Receipt interpretation preserves accounts already read when a later source fails. A message without usable purchase evidence records its own error; a refused model route stops receipt interpretation for that discovery pass instead of repeating the unavailable request for every remaining message. The report retains the route's refusal and earlier observations. A subsequent maintenance pass can resume from the retained successful interpretations.

A plan's age comes from its source fact, not when discovery happened to read it: current harness status uses the report time, and a purchase receipt uses Skrzynka's sent_at. An older receipt cannot replace a newer reported plan. Purchase evidence with a missing or invalid date is refused with the message identity and cause. Pool JSON and CLI expose discovery.plan_at_ms; Desktop shows Plan fact, epoch ms, separately from first discovery and latest observation. Retained receipt interpretations without a source date are interpreted again rather than treated as current purchases.

New members are named by provider and address, not priority. Discovery stores metadata and schedules the gateway's own sign-in through Weles on its selected host. An account that has no independent grant stays visible with its sign-in cause. Registration and a scheduled sign-in are not proof of usable capacity. Existing grants and retired members are not overwritten or reinstated.

Discovery also reads Zai account email and coding-plan tier from the harness's public metadata. A provider can declare discovery without declaring a Weles authorization or purchase capability. Such an account remains visible with its actual address, plan and source, but is not usable capacity: the missing authorization capability is retained as its grant refusal. Discovery does not copy a harness token, enable an undeclared browser login or authorize an account purchase. The existing real discovery qualification accepts the selected harness provider and Brama provider as inputs, including Zai when its actual report supplies an email.

Account observations are retained in Brama's state directory before receipt interpretation or vault inventory can delay reconciliation. An inventory refusal returns the retained observations with its cause; it does not create speculative subscription IDs or claim a grant. The next discovery pass reconciles those facts against the actual provider and account, preserving first discovery separately from the latest observation and plan date. Pending facts are cleared only after the enrollment pass persists every account successfully; concurrent reconciliation, unreadable retained state and persistence failures are explicit refusals. Older receipt interpretations missing source or discovery dates are interpreted again.

When reconciliation is refused, CLI output includes observations alongside the failure. Desktop's Account discovery result shows those addresses, reported plans, sources and first/latest observation times as awaiting reconciliation, not as registered members or usable grants. The failure beneath them explains why they have not joined the pool.

In Brama Desktop, choose Discover accounts in Subscription Pool. Discovery also runs when that view is activated and during maintenance. The resulting account rows show the same metadata and grant state as the CLI.

The Automatic sign-in report also retains checks that fail before a browser attempt, including dependency and task failures. The pool JSON exposes the current operation as automatic_sign_in.failure.stage and retains the check's code, detail and observation time in automatic_sign_in.last_check_failure. Desktop's Automatic sign-in inspector separates these from the last browser attempt and its observation time. Check failures do not pretend a browser login completed or impose a provider challenge cooldown. A later completed sign-in check or confirmed active grant supersedes the older check failure as the current failure; any retained historical check remains labelled separately.

Read and use saved resets

brama subscription list --gateway-consumer <consumer> --bearer-role <console bearer role> --refresh-usage --json
brama subscription reset codex --member <subscription-id> --reason 'restore this exhausted usage window' --gateway-consumer <consumer> --bearer-role <console bearer role> --json

Refreshing usage reads the provider's saved-credit report without consuming a credit. Each member exposes resets.offer, credit identities, remaining uses, expiry times, eligibility and any read failure. A failed read retains the older offer with its original observation time and a visible error. Desktop shows this report and provides a reasoned reset action on the selected member.

The saved-reset report separates the last check from the offer's observation time. A failed refresh advances the check time and retains its cause without making the older credit offer fresh. Both CLI and Desktop show these times and the provider's eligibility explanation, so remaining credits are not mistaken for permission to consume one.

The real reset-report refusal qualification uses a member with an already observed offer and an actual failing reset-report endpoint while provider usage remains readable. It refreshes through the CLI, verifies the new attempt and specific refusal, then reads the pool again to confirm the old offer and unchanged redemption journal. A healthy response or failure before the reset report is reached does not qualify this failure path. The journey neither changes credentials nor consumes credits.

A reset requires a declared provider protocol, the exact member, its independent Brama grant, a reason and current eligibility. Missing declarations, mismatched providers, retired members and unsupported offers are refused. Report-refresh admission refusals are retained beside provider read failures, so the member shows why no fresh report was obtained. An intent and its outcome are recorded before and after the provider request. An uncertain response is not retried: later maintenance must reconcile the selected credit's consumption before another reset can be sent. A change in eligibility alone is not consumption evidence; if the provider exposes no consumption counter, the uncertain request remains visible and no further reset is submitted.

Read-only preparation precedes mutation intent: Brama resolves the provider organization and validates the authenticated reset request before recording it as requested. A failure there records refused with reset was not sent and the failed operation; it does not create an uncertain consumption hold. After intent is durable, a missing or unreadable POST response remains unconfirmed. CLI and Desktop show the same journal outcome.

A retired member is refused before provider report reads or reset mutation: subscription <id>: retired by its owner; no reset was sent. The refusal leaves its reset journal unchanged. Desktop disables the action for retired members; direct CLI and API calls enforce the same boundary.

Automatic use reads the provider's declared policy for retained credits, minimum blocked duration and approaching expiry. Missing policy values are refused rather than replaced with defaults. Saved capacity is considered before paid acquisition; an unconfirmed reset prevents buying another account. A provider that still allows traffic is not treated as blocked merely because a displayed usage percentage looks full.

Codex expiry salvage may request a reset before the account is blocked; the provider decides whether there is useful capacity to restore. Its explicit nothing_to_reset and no_credit responses are recorded as refused, not as ambiguous consumption. No retry is sent within that operation. A later maintenance pass reads a fresh offer before deciding again. Transport failures and unrecognized outcomes remain unconfirmed and cannot authorize another mutation.

Output, state, and refusals¶

The group command itself produces only help or parser errors and changes no state. Omitting <COMMAND> or naming anything outside the list above is refused by Clap before a handler runs; use brama subscription --help to print the accepted tree. Taking a grant a coding harness already holds was removed: one OAuth pair has one holder, and a second one costs the first its session.

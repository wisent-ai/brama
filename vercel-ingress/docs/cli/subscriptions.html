Brama CLI command reference

brama subscriptions¶

Report the subscription pool this gateway routes over: every subscription, the state of its credential, its plan windows and whatever is standing in its way. Reading stored usage is read-only; refreshing usage is explicit.

This command runs where the vault and the usage ledger are, so what it proves is the installation and what it is answered about is the whole pool. The same capability answers an account holder about its own accounts and a signed agent about its own over GET /v1/subscription-pool; there is no second implementation per audience, and no list subcommand any more — the pool is one thing to report, not a group to enter.

Invocation¶

brama subscriptions [--json] [--refresh-usage]
brama subscriptions --apply --json < membership.json
InputRequired/defaultMeaning
--jsonoptional; offPrint the complete report as JSON.
--refresh-usageoptional; offRead current free provider usage reports through Brama, renewing expired OAuth grants when possible. Never starts a sign-in or sends a model request.

--apply reads one JSON membership document from standard input and cannot be combined with --refresh-usage. It runs the same operation as POST /v1/subscription-pool, with the local vault-owning process's deployment scope. The document must name agent_id; secret values are never command-line arguments.

Pool membership

A bank document carries {"action":"bank","agent_id":"my-agent","provider":"openai","api_key":"…"}. A retirement document carries {"action":"retire","agent_id":"my-agent","subscription_id":"brama-sub-my-agent-openai-primary"}. Banking persists the credential and membership; retirement disables the subscription and journals the transition without deleting the encrypted vault item. A bank receipt proves storage, not a successful model request.

The mutation always prints the JSON receipt, including when --json is omitted. Invalid JSON, an unknown field or action, a missing owner, an unknown subscription and vault failures return the same error body as HTTP and exit 1. A refused operation leaves membership unchanged. Brama Desktop's existing subscription controls use that same HTTP operation; there is no second lifecycle implementation.

The real CLI story is cargo test --test pool membership::cli_banks_and_retires_membership_and_refuses_invalid_writes. It runs brama subscriptions --apply --json with an isolated real Skarbiec vault, reads the stored ownership and disabled state, and keeps command output and source identity under .wisent-output/pool. It does not stand in for a provider authentication or inference test.

Output and state¶

Text output begins <live> of <total> subscription credentials are live, states whether the usage report is complete, and prints each account's state, provider, subscription id, windows, percentages, reset times, observation times and latest usage attempt. JSON contains ok, observed_at_ms, scope (deployment here) and the subscriptions array; every row carries id, provider, status, state, expires_at, last_redeem_error, limits, measured, block, credential, usage_check, usage_source and stale. The four states are in subscription states.

With --refresh-usage, the CLI reads the plan-usage capability in this process — the same one the gateway serves at POST /v1/plan-usage and Brama Desktop's Refresh usage reads over HTTP. Successful accounts remain visible if another fails. The last good reading survives a refusal with its original timestamp and stale: true; a missing or malformed metric never becomes zero.

Refusals¶

The command exits 1 when discovery, ledger access, or any active subscription's usage is unavailable or stale. Both output modes retain the partial result; text mode prints failure details to stderr, while JSON includes standard Wisent envelopes in errors. Each envelope names the failed operation and retains the actual cause, with the subscription or agent and attempt time in context. An inventory Brama could not read is reported as a failure with its reason — never as an empty pool, because an empty pool and an unread vault are the same picture and opposite repairs.

See the pool capability over HTTP, subscription states, or the CLI tree.

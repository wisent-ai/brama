Brama CLI command reference

brama subscription import¶

Take the Claude grant the operator’s harness already holds and make it this subscription’s credential. omp keeps every account it signed in under ~/.omp/agent/agent.db; when that harness is signed into the account the pool needs, nobody has to log in a second time. Brama reads the store, never writes it, stores the grant in the shape its refresh path reads, proves it with one minimal completion, and journals the verdict with the reason.

Invocation¶

brama subscription import <PROVIDER> --from-omp --subscription-id <ID> --reason <REASON> [--account <EMAIL>] [--store <PATH>] [--json]
InputRequired/defaultMeaning
<PROVIDER>requiredclaude-code. The harness calls it anthropic; other providers are refused by name.
--from-omprequiredRead the grant from omp’s credential store on this machine. It is the only store this command reads.
--subscription-id <ID>requiredThe exact Brama subscription whose grant this import replaces.
--reason <REASON>requiredNonempty audit reason, journaled beside the verdict.
--account <EMAIL>required when the harness holds more than one enabled grantWhich account’s grant to take. Disabled accounts are never candidates.
--store <PATH>optional; ~/.omp/agent/agent.dbAnother harness store, read the same way.
--jsonoptional; offPrint the verdict as JSON instead of labeled lines.

What happens¶

  1. The store is opened read-only and the enabled anthropic OAuth rows are read, newest first. One enabled account is taken as it is; several are refused until --account names one.
  2. The grant — access token, refresh token, expiry — is stored as the subscription’s credential, {"claudeAiOauth":{accessToken,refreshToken,expiresAt,scopes}}, the shape the refresh path reads for claude-code.
  3. Brama spends one minimal completion on the stored grant through its own dispatch. The proof is a probe, not a refresh, on purpose: a refresh rotates the refresh token and revokes the one it replaced, which would kill the harness’s copy the moment Brama proved its own and fail every session the operator has open on that account at its next refresh. The probe rotates nothing; the sweep rotates the grant later, as the access token nears its end.

Output¶

provider: claude-code
subscription: brama-sub-wisent-app-claude-primary
account: someone@example.com
result: signed_in
detail: someone@example.com's grant from the operator's harness is stored and the provider answered a completion on it; Brama will refresh it from now on

Exit status is 0 only for result: signed_in. The verdict is journaled as a subscription_sign_in record with origin: harness and the reason.

After the import¶

Two holders of one grant is a state that ends by itself: whichever side refreshes first — Brama’s sweep, or the harness — rotates the refresh token, and the other side’s next refresh is refused with invalid_grant. Brama is meant to be the one that keeps it: point the harness at Brama for inference, or sign the harness in again on its own when its copy goes stale. Nothing here disables the harness’s row.

Exact refusals¶

  • Without --from-omp: --from-omp names the only store this command reads; nothing else holds a grant Brama can take.
  • Another provider: the harness holds no grants Brama can take for `<provider>`; claude-code is the one it can.
  • Empty reason: --reason must say why this sign-in is being run.
  • A store that is not there: the harness store <path> cannot be opened: <error>; one without the harness’s table: the harness store <path> is not the store Brama knows.
  • No enabled grant: the harness holds no enabled `claude-code` grant; sign it in there first, or sign in by hand.
  • Several enabled grants: the harness holds N enabled `claude-code` grants; name one with --account: a@x, b@y; an --account the harness does not hold: the harness holds no enabled `claude-code` grant for <email>.
  • A stored grant the provider will not serve: result: failed with the grant from the operator's harness is stored, but the provider would not serve it: <the provider's sentence> — for a token the provider does not know, provider_authentication: OAuth access token is invalid.

Brama Desktop’s Take the grant from omp… on a claude-code row reads the same store on the machine the console runs on and hands the grant to the gateway through POST /v1/admin/subscription-pool/grant (HTTP API), which stores and proves it exactly as this command does.

See the by-hand sign-in, the command group or the CLI tree.

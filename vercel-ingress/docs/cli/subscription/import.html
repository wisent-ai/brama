Brama CLI command reference

brama subscription import¶

Take a grant a harness on this machine already holds and make it this subscription’s credential. Four harnesses sign accounts in on an operator’s machine and each keeps the grant its own way — omp in ~/.omp/agent/agent.db, Claude Code in ~/.claude/.credentials.json (on macOS in the Keychain under Claude Code-credentials), Codex CLI in ~/.codex/auth.json, Kimi Code in ~/.kimi-code/credentials/kimi-code.json. When one of them is signed into the account the pool needs, nobody has to log in a second time. Brama reads each store the way it was written, never writes any of them, turns what it finds into the one document its refresh path reads for that provider, proves it with one minimal completion, and journals the verdict with the reason and the harness it came from.

Invocation¶

brama subscription held [--provider <PROVIDER>] [--home <DIR>] [--json]
brama subscription import <PROVIDER> --subscription-id <ID> --reason <REASON> [--from <HARNESS>] [--account <EMAIL>] [--home <DIR>] [--gateway <ORIGIN>] [--json]
InputRequired/defaultMeaning
<PROVIDER>requiredclaude-code, codex or kimi — the providers whose grants the refresh path can renew.
--subscription-id <ID>requiredThe exact Brama subscription whose grant this import replaces. An id the pool does not hold yet becomes a new member of <PROVIDER>: storing the grant creates and tags its vault item, and brama subscriptions lists it at once. This is how the accounts a machine already holds join the pool without a sign-in window - on 2026-09-17 the pool routed every Claude call through one rate-limited account while the operator’s machine held two more with quota.
--reason <REASON>requiredNonempty audit reason, journaled beside the verdict.
--from <HARNESS>required when more than one grant is heldomp, claude, codex or kimi. omp holds grants for all three providers; the other three each hold their own provider’s.
--account <EMAIL>required when the harness holds more than oneWhich account’s grant to take. Disabled accounts are never candidates.
--home <DIR>optional; the home directoryRead every harness store below this directory instead. The Keychain is consulted only for the real home.
--gateway <ORIGIN>optionalHand the grant to this gateway through POST /v1/admin/subscription-pool/grant instead of storing it in this process. The console’s bearer — the Skarbiec item brama-desktop-model-router, field token, the one identity the admin family answers — is read from stdin, never from argv: on a machine holding the vault key, skarbiec get brama-desktop-model-router --field token | brama subscription import … --gateway <origin>. This is how the terminal or desktop beside the harness reaches a gateway on another host.
--jsonoptional; offPrint the verdict, or the list, as JSON instead of lines.

What is held¶

brama subscription held prints one line per grant — harness, provider, account, store — and never the grant itself. An account is the e-mail the harness recorded, or the one inside Codex CLI’s identity token; Kimi Code and Claude Code record none, and the line says so. Captured on the machine this was written on:

omp     claude-code  lbartoszcze@wisent.ai        /Users/me/.omp/agent/agent.db
omp     codex        lukasz.bartoszcze@gmail.com  /Users/me/.omp/agent/agent.db
codex   codex        lukasz.bartoszcze@gmail.com  /Users/me/.codex/auth.json
kimi    kimi         account not recorded         /Users/me/.kimi-code/credentials/kimi-code.json

What happens¶

  1. The grant is chosen: the one --from and --account name, or the only grant any harness here holds for the provider. Two or more are refused, naming each harness and account.
  2. It is rewritten into the document the refresh path reads — {"claudeAiOauth":{accessToken,refreshToken,expiresAt,scopes}}, {"auth_mode":"chatgpt","tokens":{access_token,refresh_token,account_id},"last_refresh"}, or {access_token,refresh_token,expires_at} — and refused before anything is stored when it carries no refresh token.
  3. It is stored as the subscription’s credential, the ledger row is marked signed in (a row the provider had disowned reads active again), and Brama spends one minimal completion on it through its own dispatch. The proof is a probe, not a refresh, on purpose: a refresh rotates the refresh token and revokes the one it replaced, which would kill the harness’s copy the moment Brama proved its own and fail every session the operator has open on that account. The probe rotates nothing; the sweep rotates the grant later, as the access token nears its end.

The Codex proof uses codex/gpt-6-astra, which the imported ChatGPT subscription can serve. It does not use gpt-5.3-codex-spark: that model can answer The 'gpt-5.3-codex-spark' model is not supported when using Codex with a ChatGPT account. even while the same grant serves GPT-6-Astra. Such a refusal describes the probe model, not an expired grant. A probe still has to succeed before the import reports signed_in.

Output¶

provider: codex
subscription: brama-sub-wisent-app-codex-primary
account: someone@example.com
result: signed_in
detail: someone@example.com's grant from codex, the harness that held it is stored and the provider answered a completion on it; Brama will refresh it from now on

Exit status is 0 only for result: signed_in. The verdict is journaled as a subscription_sign_in record with origin: harness, the harness’s name and the reason.

After the import¶

Two holders of one grant is a state that ends by itself: whichever side refreshes first — Brama’s sweep, or the harness — rotates the refresh token, and the other side’s next refresh is refused with invalid_grant. Brama is meant to be the one that keeps it: point the harness at Brama for inference, or sign the harness in again on its own when its copy goes stale. Nothing here writes to any harness.

Exact refusals¶

  • Another provider: no harness holds grants Brama can take for `<provider>`; claude-code, codex and kimi are the ones it can.
  • An unknown harness: `<name>` is not a harness Brama reads grants from; name one of omp, claude, codex, kimi; a harness that does not sign in for the provider: codex signs nothing in for `kimi`; it holds grants for codex.
  • Empty reason: --reason must say why this sign-in is being run.
  • Nothing held: no harness under <home> holds an enabled `<provider>` grant; sign one in there first, or sign in by hand; an --account nobody holds: no harness here holds an enabled `<provider>` grant for <email>.
  • Several held: N grants for `<provider>` are held here; name one with --from and --account: omp (a@x), codex (b@y).
  • A store that cannot be read says which: omp's store <path> cannot be opened: …, codex's store <path> cannot be read: …, kimi's store is not the JSON document kimi writes; the Keychain: the Keychain would not give up Claude Code's grant: …. macOS may ask the person to allow the read the first time.
  • A grant the refresh path could not renew: the grant is not the `<provider>` document Brama's refresh path reads, or carries no refresh token; Brama cannot keep a grant it cannot renew; nothing is stored.
  • A stored grant the provider will not serve: result: failed with the grant from <harness>, the harness that held it is stored, but the provider would not serve it: <the provider's sentence> — for a token the provider does not know, provider_authentication: OAuth access token is invalid.
  • With --gateway and nothing on stdin: --gateway needs the console's bearer on stdin, and stdin was empty; a gateway that refuses: the gateway refused the grant with HTTP <status>: <its sentence>.

Brama Desktop’s Take a grant a harness holds… on a pool row runs this command from the runtime it bundles, with the desktop’s own bearer on stdin, so the desktop reads no store and knows no format; the list it offers is held --json.

See the by-hand sign-in, the command group or the CLI tree.

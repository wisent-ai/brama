Brama CLI command reference

brama subscription sign-in-manual¶

Sign one account in by hand: Brama prints the provider’s authorize page, you open it in your own browser and log in, you paste the code the page shows, and Brama exchanges it for a grant, stores the grant as that subscription’s credential and proves it with one minimal completion. No Weles host, worker credential or Skarbiec login row is involved. The provider is the command’s argument; one that has no manual flow is refused by name, with the providers that have one. For claude-code the flow is the one omp auth-broker login anthropic runs, parameter for parameter, so the stored grant is the same kind the automatic refresh already keeps alive.

Invocation¶

brama subscription sign-in-manual <PROVIDER> --subscription-id <ID> --reason <REASON> [--gateway-consumer <CONSUMER> | --gateway <URL>] [--bearer-role <ROLE>] [--json]
InputRequired/defaultMeaning
<PROVIDER>requiredclaude-code. It is the only provider whose login has a manual flow; the others are refused by name.
--subscription-id <ID>requiredThe exact Brama subscription whose grant this sign-in replaces, for example brama-sub-wisent-app-claude-primary. The credential is stored under provider:claude-code:<id> with the tags discovery reads.
--reason <REASON>requiredNonempty audit reason, journaled beside the verdict.
--gateway-consumer <CONSUMER>optionalSign in on the gateway that serves the pool, found through Stado’s service directory as this consumer (the option refresh takes). The gateway draws the page, keeps the verifier, takes the paste and stores the grant in its own vault. Use it on any host that holds no vault of its own, such as a workstation.
--gateway <URL>optional; not with --gateway-consumerThe same, with the gateway’s origin named directly.
--bearer-role <ROLE>required with a gatewayThe vault role whose item’s token field is the console’s bearer. Unlike the other gateway commands the bearer cannot come from stdin, because stdin carries the pasted code.
stdinrequiredOne line: the code#state text or the whole redirect URL the page shows, pasted on the terminal or piped. The code is a credential, so it is never accepted as an argument, where the process list and shell history would keep it.
--jsonoptional; offPrint the verdict as JSON instead of labeled lines.

What happens¶

  1. Brama draws a PKCE verifier and a state, and prints https://claude.ai/oauth/authorize?… carrying the client id 9d1c250a-e61b-44d9-88ed-5944d1962f5e, the scopes org:create_api_key user:profile user:inference user:sessions:claude_code user:mcp_servers user:file_upload, the redirect http://localhost:54545/callback and the S256 challenge. Nothing has been contacted yet.
  2. You open that page in your own browser, sign into the account you want in the pool, and approve. The page then shows a code, or the browser lands on the localhost redirect; either the shown code#state or the whole redirect URL is what you paste.
  3. Brama checks the pasted state is the one it drew, exchanges the code at https://api.anthropic.com/v1/oauth/token, and stores {"claudeAiOauth":{accessToken,refreshToken,expiresAt,scopes}} as the subscription’s credential — the shape the refresh path reads for claude-code.
  4. Brama spends one minimal completion on the stored grant through its own dispatch. The result on the terminal is the provider’s answer, not the stored bytes: a grant that was stored and never exercised is exactly the state the pool was in before this command existed. The proof is a probe rather than a refresh so that a grant shared with another holder — see import — is not rotated out from under it; the sweep refreshes the grant later, as the access token nears its end.

Output¶

provider: claude-code
subscription: brama-sub-wisent-app-claude-primary
account: someone@example.com
result: signed_in
detail: someone@example.com's grant from the code the operator pasted is stored and the provider answered a completion on it; Brama will refresh it from now on

With --json the same five fields arrive as one object. account is the e-mail the provider returned with the grant, when it returned one. Exit status is 0 only for result: signed_in.

Exact refusals¶

  • Another provider: a manual sign-in is defined for claude-code; `<provider>` is not it. No page is printed.
  • Empty reason: --reason must say why this sign-in is being run. No page is printed.
  • A host that holds no vault of its own (Stado routes it to the vault owner, and Skarbiec refuses the leftover copy on it), run without a gateway: no sign-in was started: the grant could not be stored on this host (<Skarbiec's sentence>); name the gateway that serves the pool with --gateway-consumer <CONSUMER> --bearer-role <ROLE> (or --gateway <URL> --bearer-role <ROLE>) so it stores the grant in its own vault. No page is printed, so nobody logs in for a grant the gateway would never read.
  • A gateway named without --bearer-role, or --bearer-role without a gateway: clap refuses the arguments and exits 2, because the bearer cannot come from stdin.
  • The gateway refusing either step: the gateway refused to begin the sign-in: <status>: <its whole answer> or the gateway refused to complete the sign-in: …, for example subscription not found, retired subscriptions cannot be signed in, a bearer that is not the console’s, or no manual sign-in with that id is open when the gateway restarted between the page and the paste.
  • A gateway that holds the subscription under another provider: no sign-in was started: the gateway holds <id> as a <provider> subscription, not <PROVIDER>.
  • A gateway that cannot be reached, or answers something other than JSON: the gateway at <url> did not answer: <cause>, or the gateway's answer to begin the sign-in (<status>) is not JSON: <cause>.
  • Empty paste: nothing was pasted.
  • A paste that is neither code#state nor a URL with both: paste the `code#state` the page shows, or the whole redirect URL.
  • A paste from another sign-in or a stale page: the pasted state is not the one this sign-in started with; open the URL again and paste what that page shows.
  • The provider rejecting the code: result: failed with the provider refused the code with HTTP <status>: <body>; nothing is stored.
  • A grant without a refresh token: the provider's answer carries no refresh token; Brama cannot keep a grant it cannot renew; nothing is stored.
  • A stored grant the provider then would not serve: result: failed with the grant from the code the operator pasted is stored, but the provider would not serve it: <the provider's sentence>. The account is usually not entitled to the client — the same oauth_not_allowed_for_organization a lapsed organisation returns on every path.

Every refusal exits 1. The verifier and the grant live only in this process’s memory and are zeroed when it ends.

When to use it¶

When the pool has no live Claude credential and the account that works is one a person can log into but Weles cannot — no login row in Skarbiec, a second factor Weles does not hold, or simply the laptop the person is sitting at. Automatic renewal takes the grant from there; the manual step is not repeated until the provider revokes the refresh token.

Without a gateway the command runs where Brama runs, in the deployment’s Skarbiec environment, because that is where the grant is stored; the browser can be anywhere, since only the printed page and the pasted code cross between them. When the person sits at another host than the gateway, --gateway-consumer (or --gateway) with --bearer-role does the same two steps through POST /v1/admin/subscription-pool/sign-in-manual and POST /v1/admin/subscription-pool/sign-in-manual/:sign_in_id (HTTP API), as Brama Desktop’s Sign in by hand on the selected account does: the verifier stays in the gateway, the page opens on the person’s machine, the paste travels back, and the grant lands in the vault the serving gateway reads.

See the Weles-driven sign-in, the command group or the CLI tree.

Brama CLI command reference

brama subscription sign-in¶

Sign one provider account in and prove the repair. Who logs in is stated every time with --by: weles asks Weles to drive the account’s sign-in row and proves the result with Brama’s refresh path; hand prints the provider’s authorize page for you to open in your own browser, reads the code it shows on stdin, stores the grant and proves it with one minimal completion. One operation with two methods is one verb; nothing is assumed when --by is left out.

Invocation¶

brama subscription sign-in <PROVIDER> --by weles --reason <REASON> [--subscription-id <ID>] [--login-item <LOGIN_ITEM>] [--json]
brama subscription sign-in <PROVIDER> --by hand --subscription-id <ID> --reason <REASON> [--gateway-consumer <CONSUMER> | --gateway <URL>] [--bearer-role <ROLE>] [--json]
InputRequired/defaultMeaning
<PROVIDER>requiredOne of codex, claude-code, or kimi. --by hand has a manual flow for claude-code only; the others are refused by name.
--by weles|handrequired; no defaultWho logs the account in: Weles through its sign-in row, or you in your own browser.
--reason <REASON>requiredNonempty audit reason recorded with the sign-in verdict.
--subscription-id <ID>--by hand: required. --by weles: optional only when exactly one active subscription matchesThe exact Brama subscription whose grant is replaced and proved. Automatic renewal always supplies it.
--login-item <LOGIN_ITEM>--by weles only; optionalAn exact Skarbiec login reference. Otherwise the identity and login method are resolved from Skarbiec; no Weles account registration is required.
--gateway-consumer <CONSUMER>--by hand only; optionalSign in on the gateway that serves the pool, found through Stado’s service directory as this consumer. The gateway draws the page, keeps the verifier, takes the paste and stores the grant in its own vault. Use it on a host that holds no vault of its own, such as a workstation.
--gateway <URL>--by hand only; optional; not with --gateway-consumerThe same, with the gateway’s origin named directly.
--bearer-role <ROLE>required with a gatewayThe vault role whose item’s token field is the console’s bearer; it cannot come from stdin, which carries the pasted code.

--jsonoptional; offPrint the verdict as JSON instead of labeled lines.

By Weles¶

Output and state¶

Brama calls Weles's authenticated POST /reauth/resolve to resolve the exact Skarbiec identity without opening a browser. It passes account_revision to POST /reauth, checks the response and refreshes the persisted credential. The saved verdict includes the subscription, login reference, account and software revisions, Weles run_id and observed second_factor. A failure also retains its stage and HTTP status. The CLI, Desktop and automatic renewal share this implementation; automatic renewal does not require a separate sign-in command.

Brama Desktop's explicit Sign in action targets the selected account through POST /v1/admin/subscription-pool/sign-in with "by": "weles", POST /v1/admin/subscription-sign-in/:agent_id/:subscription_id, or POST /v1/account/subscription-sign-in/:subscription_id. The body names a nonempty reason and optional login_item; the pool route additionally requires subscription_id and by. Brama verifies ownership and derives the provider from that subscription. The sign-in runs until Weles reports how it ended. The app does not launch a local browser, and neither listing nor refreshing usage invokes this action.

Second-factor challenges¶

Weles answers an offered authenticator challenge with the stored seed. Without a seed, it selects an offered Google phone approval and waits for Google's result. The run then waits for a person: weles runs list and weles runs show <run> show what it asked for (Runs waiting for a person), as does Weles Desktop's Running screen on the managed worker. Approve it on the account owner's phone; nothing else is needed when Google moves on. When the prompt never arrived or nothing moved after approving, weles runs answer <run> --not-received | --approved tells the run; weles runs cancel <run> --detail <why> ends the wait.

Only the structured google_2fa_material_missing refusal starts authenticator enrolment. Brama binds that attempt to the same resolved subscription and login, confirms the Weles run and Skarbiec seed readback, then signs that account in again and refreshes its credential. A failed enrolment remains a failed sign-in, with its actual cause; Brama does not loop or silently replace an existing authenticator.

In Brama Desktop, select an account and open Second factor to see the observed challenge, method, stored seed state and seed-read error. required: false means Google did not ask during that observed sign-in, not that the account has disabled two-factor authentication. A sign-in without challenge evidence remains unobserved.

Exact refusals¶

  • Unsupported provider: Weles does not support subscription authentication for <provider>.
  • Empty reason: --reason must say why this sign-in is being run.
  • Missing admission credential: when BRAMA_WELES_REAUTH_TOKEN is unset, Brama reads the item playing role brama-weles-reauth; no such item is refused with no vault item carries stado:role:brama-weles-reauth, and two with the number of items that carry it.
  • Identity failures name the Skarbiec subscription and distinguish subscription_identity_missing, skarbiec_login_missing, conflicting login material and a changed account revision.
  • Weles execution failures retain the actual failure.code, stage, provider HTTP status and run_id. An unreadable or lost execution response is unconfirmed, not proof that no browser ran.
  • A phone approval that Google does not complete reports google_push_not_approved; a sign-in Google itself ends while the approval is awaited (a page under accounts.google.com/info/, such as sessionexpired) reports google_sign_in_ended_during_approval with that page and when the approval was asked. A method that cannot be selected reports its observed challenge rather than treating it as no second factor.
  • Enrolment preserves authenticator_replacement_requires_consent, setup_confirmation_unobserved and vault-read errors. A failed totp-seed-state operation is not evidence that a seed is missing.

An unconfirmed Weles response or a refresh that obtains nothing returns a failed verdict and exits 1; Brama never guesses between accounts.

By hand¶

No Weles host, worker credential or Skarbiec login row is involved. For claude-code the flow is the one omp auth-broker login anthropic runs, so the stored grant is the kind the automatic refresh keeps alive.

  1. Brama draws a PKCE verifier and a state and prints the provider’s authorize page. Nothing has been contacted yet.
  2. You open it in your own browser, sign into the account you want in the pool and approve; paste the code#state the page shows, or the whole redirect URL.
  3. Brama checks the state is the one it drew, exchanges the code at the provider’s token endpoint and stores the grant as the subscription’s credential.
  4. Brama spends one minimal completion on the stored grant: a probe, not a refresh, so a grant shared with another holder is not rotated out from under it.

The verdict lists the provider, subscription, account, result and detail; --json prints the same fields as one object, and the exit status is zero only for result: signed_in. Without a gateway the command runs where Brama runs, because that is where the grant is stored. With --gateway-consumer (or --gateway) and --bearer-role the serving gateway does the two steps through POST /v1/admin/subscription-pool/sign-in with "by": "hand" and …/sign-in/:sign_in_id (HTTP API), as Brama Desktop’s Sign in by hand does.

Exact refusals¶

  • Another provider: a manual sign-in is defined for claude-code; `<provider>` is not it. No page is printed.
  • A host that holds no vault of its own, run without a gateway: no sign-in was started: the grant could not be stored on this host (<Skarbiec's sentence>); name the gateway that serves the pool with --gateway-consumer <CONSUMER> --bearer-role <ROLE> (or --gateway <URL> --bearer-role <ROLE>) so it stores the grant in its own vault.
  • The gateway refusing either step: the gateway refused to begin the sign-in: <status>: <its whole answer> or the gateway refused to complete the sign-in: …; a gateway that holds the subscription under another provider: no sign-in was started: the gateway holds <id> as a <provider> subscription, not <PROVIDER>.
  • The paste: nothing was pasted; paste the `code#state` the page shows, or the whole redirect URL; the pasted state is not the one this sign-in started with; open the URL again and paste what that page shows.
  • The provider: the provider refused the code with HTTP <status>: <body>; the provider's answer carries no refresh token; Brama cannot keep a grant it cannot renew; the grant from the code the operator pasted is stored, but the provider would not serve it: <the provider's sentence>.

Flags that contradict the method¶

  • --by hand with --login-item: --login-item <LOGIN_ITEM> names a Weles sign-in row, and --by hand signs in through your own browser; drop it or sign in --by weles.
  • --by hand without --subscription-id: --by hand replaces one subscription's grant; name it with --subscription-id.
  • --by weles with a gateway or --bearer-role: --gateway, --gateway-consumer and --bearer-role carry a sign-in --by hand to the serving gateway; --by weles runs on the host that reaches Weles, so drop them or sign in --by hand.
  • No --by, a gateway without --bearer-role, or --bearer-role without a gateway: clap refuses the arguments.

These are usage errors, refused before anything is contacted, with clap’s usage exit status.

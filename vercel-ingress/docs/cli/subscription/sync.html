Brama CLI command reference

brama subscription sync¶

Every grant a harness on this machine holds joins the pool, without anyone naming it. On 2026-09-17 the pool refused every Claude call — all bounded 'claude-code' credentials unavailable for agent — while the operator was talking to Claude on the same machine, on an account no pool member named. The accounts were added by hand, one import at a time, and the operator’s answer was that this is the opposite of how it should work: the pool has to see every account the machine holds by itself. This is that sweep.

Invocation¶

brama subscription sync --reason <REASON> [--home <DIR>] [--gateway <ORIGIN>] [--json]
InputRequired/defaultMeaning
--reason <REASON>requiredNonempty audit reason, journaled beside every verdict the sweep produces.
--home <DIR>optional; the home directoryRead every harness store below this directory instead, as held and import do.
--gateway <ORIGIN>optionalHand the grants to this gateway instead of storing them in this process; the console’s bearer is read from stdin once. Brama Desktop runs the sweep this way from the runtime it bundles.
--jsonoptional; offPrint {"ok", "grants": [{"harness", "provider", "account", "subscription_id", "result", "detail"}]} instead of lines.

What it does¶

  • Lists what every harness holds — omp, Claude Code, Codex CLI, Kimi Code — exactly as held does; disabled accounts are never candidates.
  • Derives one stable member id per account: brama-sub-held-<provider>-<account>, both folded to the resource alphabet (controlyourai@gmail.com becomes controlyourai-gmail-com). The same account gives the same id on every sweep.
  • Reads the pool where it will write — the gateway’s GET /v1/subscription-pool, or this process’s own report — and reports an id already there with a usable grant as present without touching it: Brama refreshes that grant itself, and the harness’s copy is stale the moment it did. A member whose grant was taken from a harness is borrowed: the harness refreshes it on its own clock, so Brama never rotates it — on 2026-09-17 Brama refreshed two grants taken from omp, the provider revoked the refresh tokens omp held, and the operator’s own session lost its account within the hour. The sweep hands every borrowed grant over on every pass; the gateway answers unchanged when the harness has not rotated it (nothing stored or proved) and stores and proves the new one when it has. A member the pool has disowned (burnt) is taken again the same way. The pool report names the harness in credential.borrowed_from.
  • Imports every id not yet present through the same path import takes: the grant is stored (a new id becomes a new member under its provider), proved with one minimal completion, journaled with the harness it came from, and reported as imported; a grant the provider would not serve is failed with the provider’s sentence.
  • A grant whose harness records no account is unnamed: no member can stand for it. Kimi Code’s store records none.
  • Exits unsuccessfully when any grant failed; present and unnamed rows do not fail the sweep.

Exact refusals¶

  • Empty reason: --reason must say why this sync is being run.
  • With --gateway and nothing on stdin: --gateway needs the console's bearer on stdin, and stdin was empty; a gateway that refuses the pool report: the gateway refused the pool report with HTTP <status>: <its sentence>; a gateway that refuses one grant: that grant’s row reads failed with the gateway refused the grant with HTTP <status>: <its sentence>.
  • A store that cannot be read refuses the whole sweep with held’s own sentence, because a sweep that silently skips a harness would report a machine as swept when it was not.

Brama Desktop runs this sweep by itself: once when its gateway is connected and every thirty minutes after, from the runtime it bundles with the desktop’s own bearer on stdin, and its Subscription pool screen says what the last sweep did — which accounts joined, which were already there, which the provider refused — with Sweep now beside it. Nothing on this machine has to be named for the pool to route over it.

See held and import, the command group or the CLI tree.

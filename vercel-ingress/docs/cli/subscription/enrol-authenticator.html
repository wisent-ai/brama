Brama CLI command reference

brama subscription enrol-authenticator¶

Ask Weles to enrol an authenticator for the Skarbiec login behind one subscription, and confirm with Skarbiec that the seed landed. It is the repair for the one refusal a sign-in cannot repair itself.

Why it exists¶

An automatic sign-in stops at google_2fa_material_missing when the login carries no authenticator seed, and no sign-in can produce one: the provider shows a setup key only inside a signed-in session. The enrolment trajectory signs in with the stored password, waits once for the operator's phone approval, opens the account's authenticator setup, reads the key behind Can't scan it?, confirms the first code and writes the key to the login item. After it, every later sign-in for that account answers the second factor by itself — which is the difference between this and pasting a one-time code, a repair that renews one grant and leaves the next sign-in stopping in the same place.

Invocation¶

brama subscription enrol-authenticator <PROVIDER> --subscription-id <ID> --reason <REASON> [--login-item <LOGIN_ITEM>] [--login-timeout-ms <MILLISECONDS>] [--json]
InputRequired/defaultMeaning
<PROVIDER>requiredOne of codex, claude-code, or kimi.
--subscription-id <ID>requiredThe Brama subscription whose login gains the authenticator. Weles resolves which vault row that is, exactly as it does for a sign-in.
--reason <REASON>requiredWhy this enrolment is being run; recorded beside the verdict.
--login-item <LOGIN_ITEM>optionalAn exact Skarbiec login reference, for a subscription whose identity names more than one.
--login-timeout-ms <MILLISECONDS>optional; 900000Maximum time Weles may spend driving the browser, including the wait for the phone approval.
--jsonoptional; offPrint the verdict as JSON instead of labeled lines.

Output and state¶

Brama resolves the account through Weles's POST /reauth/resolve, then orders the enrolment with POST /reauth/enrol-authenticator — admitted by the same brama-weles-reauth bearer the sign-in uses, never by Weles's general worker token. Afterwards it asks Skarbiec whether that login now holds a usable seed, through totp-seed-state, which reports the state of the field and never its value. The verdict is enrolled only when the vault agrees; a run that answers ok while the seed is absent is reported as not_enrolled and exits 1, because the next sign-in would stop in the same place.

provider: codex
subscription_id: brama-sub-wisent-app-codex-primary
login_item: codex-wisent-google-sso
result: enrolled
detail: Weles enrolled an authenticator for codex-wisent-google-sso and Skarbiec now holds its seed; every later sign-in for codex answers Google itself

Exact refusals¶

  • A provider with no Weles sign-in: provider `<provider>` has no Weles sign-in, so it has no authenticator to enrol.
  • A login that signs in with a password: authenticator_enrolment_unsupported_login_method, naming the login and its method — there is no authenticator on it to enrol.
  • Missing admission credential: BRAMA_WELES_REAUTH_TOKEN is unavailable; Brama must acquire brama-weles-reauth/token from Skarbiec at startup.
  • A worker that does not serve the route answers HTTP 404, which is what a deployment older than this release reports.
  • Every stop inside the trajectory keeps its own name — google_push_not_approved, setup_key_not_shown, setup_code_rejected, seed_persist_unconfirmed — and the key is redacted from any page preview.

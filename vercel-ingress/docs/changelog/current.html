Brama changelog: current changes

Current changes¶

Entries without a release coordinate are recorded here as unpublished. The unreleased changes to the subscription pool and its credentials have their own page. Released entries live in 0.4.46 to 0.4.13, 0.2.77 to 0.2.42 and 0.2.5 to 0.2.2. Brama follows Semantic Versioning and the pre-one compatibility policy in RELEASE.md.

Image, video and voice, and a catalogue that says what a model is¶

Brama routed text. It now routes the three generation shapes that are not text: POST /v1/images/generations, POST /v1/videos with GET /v1/videos/{id} reading the job back, and POST /v1/audio/speech, whose answer is the provider's encoded audio rather than JSON. Three aliases reach them — image-model, video-model, voice-model — known by name and required of nobody, so a deployment that generates no media changes no policy to take this release. Media is paid by the deployment's own capability: no subscription in the pool carries an image, video or voice quota, so best cannot stand behind a media alias, and the registry refuses one that tries.

Which providers serve which shape is declared from their vendor documentation and nowhere else: openai for all three, xai and together for images, venice for images and voice, groq for voice. A provider that generates media behind a different contract is declared with empty media paths and refused by name.

The catalogue now says what a model is. Every model carries kind — text, image, video or audio, decided from the output modalities its source declares — and openWeights, which is the catalogue's own flag and is null where the source said nothing, a different answer from false. Until now outputModalities read ["text"] for every id including the image and video models the catalogue had always carried, so no console could tell a renderer from a chat model.

Categories are the operator's, not the gateway's. A category is declared in the route registry — by provider, by exact route, or by a term the publisher put in the model's name — and uncensored is the first one anybody asked for. Brama infers none: a gateway that guessed would be publishing an opinion as metadata. GET /v1/models narrows on kind, weights, category and provider and refuses any other query member by name; GET /v1/categories reports each declaration with how many models it currently holds, which is the check on the declaration. The shell surface is brama models, brama categories, brama image, brama video and brama speak; the console carries the same facets, the same declarations and the same three generation shapes.

Typed decisions: decision-model and best-decision-model¶

Brama served one shape until now: generation. A caller that needed a routing decision, a gate or a grade asked a chat model for prose and parsed it, and every caller parsed it differently. POST /v1/decisions takes a state and a map of typed questions — a noul, a choice over the options the caller declared, a score over the rubric it gave — and answers one typed answer each. Two aliases reach it and no other name does: decision-model for a route this deployment pays for, and best-decision-model, whose route may be best, so the caller's own signed identity selects the subscription that pays.

Two engines answer and the response says which. TypeSafe AI's System One model is declared as the typesafe provider and answers the decision wire natively; because it generates no text it carries no chat path at all, and a chat call naming one of its routes is refused rather than sent to a URL this build invented. Every other route is served by asking a chat model for the probability mass over each question's declared labels, and Brama computes the choice, the score and the confidence from that distribution itself — so the model cannot contradict its own numbers, and an answer outside the declared schema is refused decision_contract_violated rather than passed on.

The two aliases are known by name and required of nobody: unrouted, they report no_route with the command that repairs them, so no managed deployment has to change its policy to take this release. brama decide answers one from an operator shell, and brama routes set and brama routes rm declare and retire an alias through the same validated, atomic, owner-only registry write the admin route performs.

Two things found on the way and fixed with it. A model-scoped bearer could not reach /v1/decisions at all, because the path allowlist enumerates the inference paths. And brama aliases in an operator shell answered capability_absent for every provider whose credential the very next step would have read: the presence check parsed a file named by a variable only the launcher sets, while the credential path asks Skarbiec. It asks Skarbiec too now, once per provider. /v1/admin/snapshot additionally reports the endpoint each provider resolves, or why it resolves none.

Unreleased: an alias resolves to exactly one route¶

An alias now names one destination and nothing else. When that route refuses, the refusal is what the caller receives: no second route is attempted, so the answer an operator reads is the answer the route gave. The request deadline is the deadline of that one attempt and is not multiplied by a number of routes.

The route registry document carries exactly three known top-level fields: schema_version, whose value is the number one, deployments, and routes, which maps an alias to its single destination. Any other top-level field is refused by the deserializer, so a document that carries one is rejected whole rather than partly read.

PUT /v1/admin/routes takes exactly the two fields below and DELETE /v1/admin/routes takes {"alias"}; both answer {"ok":true,"routes":<document> } with the committed document.

{"alias": "wisent-backend", "primary": "codex/gpt-5.3-codex-spark"}

GET /v1/aliases returns rows of {"alias", "state", "route", "reason", "required", "authorized"}, and the four alias states are unchanged: serving, no_route, capability_absent and routes_file_invalid. A completion that names a declared alias which cannot serve is 503 alias_unserviceable carrying details.state and details.route; an unknown alias is 404 whose details also carry state and route. brama aliases prints alias, state and route, and brama adopt reviews one route per alias.

brama routes migrate is new and is how an existing registry file reaches this shape without hand editing. It reads the configured document, keeps only the known top-level fields, validates the result, and commits it with the same atomic owner-only replacement every other registry write uses. It is idempotent and prints the resulting document, so a second run reports the same document the first run committed.

Unreleased: subscription plan usage replaces four invocations¶

One sweep and one ledger were asked for four ways — POST /v1/subscription-usage/:agent_id, POST /v1/account/subscription-usage, POST /v1/admin/subscription-usage/:agent_id and POST /v1/admin/subscription-pool/usage — and every one of them read the same usage ledger and the same provider reports. One capability answers it now: POST /v1/plan-usage, scoped by the identity the caller proved through the same resolver the subscription pool uses. All four were deleted in the same change: their routes, their handlers, the Brama Desktop calls that reached them, and their paragraphs on this site.

The answer is the pool's document with every reading brought current, so a row means the same thing whichever capability produced it. A provider that answered sets limits and usage_source: "provider"; a provider that refused keeps its last reading, marks it stale, and records the refusal in errors in the provider's own words; a provider with no supported free report is recorded as exactly that. None of the three reads as a plan reported unused. A request body is refused with plan usage takes no request fields; the answer follows from the proven identity, and an inventory Brama could not read stops the provider reads rather than asking about accounts nobody confirmed.

A model-scoped bearer may now reach the capability, which every workload identity the authority resolves is: none of the four routes it replaced was reachable by one, so the single audience that signs its own requests could not read its own plan usage over any of them. brama subscriptions --refresh-usage and Brama Desktop's Refresh usage both read this capability. tests/usage drives it over real HTTP against an isolated vault, an isolated Wisent Identity authority and an isolated endpoint answering the providers' own usage reports.

Unreleased: the subscription pool replaces eleven invocations¶

Which subscriptions exist and who owns them was asked eleven ways — brama subscriptions list; GET, POST and DELETE /v1/subscriptions/:agent_id; GET and POST /v1/account/subscriptions; DELETE /v1/account/subscriptions/:subscription_id; GET and POST /v1/admin/subscriptions/:agent_id; DELETE /v1/admin/subscriptions/:agent_id/:subscription_id; and GET /v1/admin/subscription-pool — and every one of them answered it from the same vault declaration. One capability answers it now: GET and POST /v1/subscription-pool, scoped by the identity the caller proved, plus brama subscriptions as a leaf command. All eleven were deleted in the same change: their routes, their handlers, their tests, the Brama Desktop calls that reached them, and their paragraphs on this site. brama subscriptions list no longer parses.

The pool document is one shape for every audience — {"ok", "observed_at_ms", "scope", "errors", "subscriptions"} — so the per-audience providers key and the agentId key are gone, and the row key subscription_id is now id, which every row already carried. scope is deployment or the agent id the answer was narrowed to. A write names an owner only from the deployment scope; an agent or account holder that sends agent_id is refused with agent_id is derived from the proven identity and must not be sent, and a deployment-scoped write that omits it is refused too. Retiring a subscription the caller does not own is 404 subscription not found even when the deployment holds it.

BRAMA_WISENT_AUTH_URL now selects the Wisent Identity origin, and an unset variable means canonical Wisent Supabase. The anon key was already deployment-configurable while the origin it was presented to was compiled in, which left the human half of every identity decision unprovable anywhere except against the production project; the account holder's scope is now driven end to end in tests/pool.

The measured command surface is 42 leaf invocations in 6 groups at 15c27474b3a870e1a399697068e2b96f4e72d8dd, down from 50 in 7 (command surface).

Unreleased: the backend alias is the client's name¶

The Wisent App backend's chat alias is wisent-backend. It was wisent-backend/chat/primary beside a rank-suffixed twin, which spelled in the alias name the same rank that the registry's own per-alias column of spare destinations then carried; that column is removed by the current contract, under which an alias carries exactly one route. The name then became wisent-backend/chat, which spelled a shape POST /v1/chat/completions already names. The alias now carries only who is asking. wisent-backend/embeddings and wisent-backend/moderation keep their purpose segment for one stated reason: each needs a route of its own and the registry is keyed by alias name alone.

Unreleased: subscription usage and failure reporting¶

brama subscriptions list --refresh-usage and Brama Desktop's Refresh usage share native free provider reports, bounded credential access and OAuth renewal. Account rows retain their last readings, reset and observation times, independent usage_check results and complete stored failure causes. Discovery, storage, malformed replies and partial refresh failures are all reported as themselves rather than as a healthy empty pool. An integration whose provider publishes no free report is recorded as unmeasured, which is not the same row as a plan measured at zero.

Desktop exposes the same account-specific errors, retained stale windows and explicit Weles/Stado Sign in action. A missing measurement time is reported as unknown. Refresh operations may wait longer than ordinary reads so that a provider or credential refusal is reported by Brama itself rather than by the caller's own transport. No OMP integration is used.

Signing an account in is the gateway's own work. Until 2026-09-09 the whole escalation sat behind BRAMA_CREDENTIAL_AUTOMATIC_SIGN_IN=1, which no host set, so a credential a provider had disowned waited for someone to run a command; that variable is gone and the sweep asks Weles by itself. A stored document that is not a credential is no longer read as a healthy grant either: it has no expiry, the sweep called it NotDue forever, and it is now recorded as needing a sign-in and handed to Weles. Everything that can stop that loop is named per account — automatic_sign_in on every pool row, automatic_sign_in.blocked in the readiness answer, and one of eight blocked_by words listed in the credentials runbook — including a gateway running on a host the registry does not place one on.

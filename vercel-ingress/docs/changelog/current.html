Brama changelog: current changes

Current changes¶

The image selection and Codex changes below shipped in 0.4.14 and 0.4.13. Entries without a release coordinate remain recorded as unpublished. Earlier released entries live in 0.2.77 to 0.2.42 and 0.2.5 to 0.2.2. Brama follows Semantic Versioning and the pre-one compatibility policy in RELEASE.md.

0.4.14: image-aware best selection¶

A best request with image content now filters the caller's active pool for advertised image input before applying a preferred route. Buffered and streaming requests use the same rule. No eligible model means a visible refusal, not a text-only substitution or a broader permission.

The real image qualification checks the visible heading through both HTTP response modes and preserves the out-of-scope model refusal. No credential, route, state schema or billing migration is required.

Published to the candidate channel from cbd297df3ed1efd961078b4aa45e7fca8f323b0f through Stado run 4394248ac72d40c7a9e1adc0e88d3d0c on 2026-09-15 for Darwin arm64 and Linux amd64. The deployed gateway reported that exact revision. All three real image qualification cases passed: buffered reading, streamed reading and the unchanged HTTP 403 refusal of an unauthorized route. Weles 0.7.3 separately passed its real text, image and invalid-token cases against this gateway.

0.4.13: Codex imports and concurrent discovery¶

Released from 4577501971ffcec56a3b4c16f064fe1299d5cdc7 through Stado run c3510d34e8aef6f70c19f8c930394176 on 2026-09-15, for Darwin arm64 and Linux amd64. The gateway on charless-mac-mini reported that exact revision, ready: true and degraded: false. A completion probe against each imported Codex account returned HTTP 200 and probe.ok: true.

Importing either existing OMP Codex account stored its grant but returned failed because the verification request selected gpt-5.3-codex-spark, which the provider refused for ChatGPT accounts. The same grants served codex/gpt-6-astra through Brama. The Codex probe now uses GPT-6-Astra, including the probe after a CLI or desktop import. It still proves a real completion and never refreshes the borrowed grant during import. An actual provider refusal remains a failed import, with the provider's sentence.

The real held-grant journey uses the existing isolated gateway and Skarbiec fixture, with refresh and usage sweeps disabled. Run cargo test --test subscriptions_harness_grants a_real_held_codex_grant_is_accepted_and_probed -- --nocapture with BRAMA_REAL_HARNESS_HOME and BRAMA_REAL_CODEX_ACCOUNT selecting the existing OMP account. The operator vault and harness store are not written. Receipts, source revision and the persisted pool response remain under target/real-import-evidence/; an unheld account must leave the stored grant unchanged.

The first release build found that a nested build path made all seven real pool journeys fail before opening their vault: GnuPG reported File name too long for its Unix socket. Only these socket-owning fixtures use the workshop's short-root exception, ~/.brama/test-runs/<unique>, with owner-only permissions and removal when the fixture closes. Ordinary test directories and retained evidence still belong under Cargo's target/.

GPT-6-Astra is now also advertised by the Codex catalogue, so a client allowed to use that route receives an available model instead of an empty list. Concurrent first catalogue requests share one discovery per subscription; the real held-grant journey proves six authenticated clients receive the model with one reported credential read, rather than six. The same coalescing covers the startup readiness sweep without weakening its checks or reusing inference credentials.

Unreleased: a Claude Code grant travels in Claude Code's own shape¶

With the temperature gone, the deployed gateway's first best request as tama was still refused: Anthropic answered 429 with the one-word body Error for claude-code/claude-fable-5-1 and then for claude-sonnet-4-6, while claude-haiku-4-5 had answered the import probe minutes earlier and omp was being answered on the same account for the same models. The grant was fine; the request was not Claude Code's. A request that presents a Claude Code grant now carries what Claude Code carries — its user agent and beta list, x-app: cli, and a system prompt opened by the billing attestation with a checksum of the body and the sentence You are Claude Code, Anthropic's official CLI for Claude. — on the buffered and streaming paths alike (how a request presents it).

Unreleased: an omitted temperature is not invented¶

The first Claude completion through the deployed gateway after the pool was repaired was refused by the provider: claude-code/claude-opus-4-7 refused (provider_failure: `temperature` is deprecated for this model.), and the same for claude-opus-4-8. The caller had sent no temperature; the gateway defaulted it to 0.7 on every inbound format and sent that default to every provider as a real setting. A temperature now reaches the provider only when the request stated one, on the chat, Anthropic messages and Responses wires and on every provider dialect; a stated value is bounded as before. The gateway's own probes still pin zero, because a probe's answer should not vary (shared validation).

Unreleased: a grant any harness already holds is taken, not asked for again¶

On 2026-09-13 the operator asked why Brama did not simply take the tokens from omp, and then why only from omp: the harnesses beside the gateway had been signed into the accounts the pool needed for a day. Four harnesses sign accounts in on an operator's machine - omp, Claude Code, Codex CLI, Kimi Code - and each keeps the grant its own way. brama subscription held lists what every one of them holds, never the grants; brama subscription import <provider> --from <harness> --subscription-id <id> --reason <why> reads that harness's own store read-only, rewrites the grant into the document the refresh path reads for claude-code, codex or kimi, refuses one it could not renew before storing anything, stores it as the subscription's credential, marks the row signed in, proves it with one minimal completion, and journals the verdict with the harness it came from. With --gateway and the console's bearer on stdin the same command hands the grant to a gateway elsewhere through POST /v1/admin/subscription-pool/grant; Brama Desktop's Take a grant a harness holds… runs it from the runtime it bundles, so the desktop reads no store and knows no format.

Running that against the deployed gateway found the admin family unreachable in production: every /v1/admin/* path answers only a brama-desktop identity with no allowlist, such an identity can only come from the boot table, and the launcher never put one there - the authority resolves a workload bearer with the routes it was issued, never without them. Brama Desktop and the terminal alike were answered 401 model_bearer_unrecognized; only the test harness, which seeds the console into the table, ever reached the family. The launcher now projects brama-desktop-model-router#token - the item the desktop acquires - into the boot table as brama-desktop, optional like the renewal client, and says on its stderr when it could not read it (who the admin family answers).

Every grant that reaches Brama without a Weles sign-in - pasted code, harness, console - is now proved by a probe instead of a refresh. A refresh rotates the refresh token and revokes the one it replaced, so proving a grant the harness still holds would have killed the harness's copy and failed every session the operator had open on that account at its next refresh; the probe spends one completion on the access token both sides hold and rotates nothing. The sweep rotates the grant later, as the access token nears its end, and the harness's copy goes stale then - which the import page says plainly.

Unreleased: a Claude account is signed in by hand, without Weles¶

brama subscription sign-in-manual claude-code --subscription-id <id> --reason <why> prints the provider's authorize page, waits for the code the operator pastes after logging in with their own browser, exchanges it at the provider's token endpoint, stores the grant as that subscription's credential in the shape the refresh path reads, and proves it with one completion. The page carries the client id, scopes, loopback redirect and PKCE challenge that omp auth-broker login anthropic sends, so the grant is the same kind the automatic renewal already keeps alive; the manual step is not repeated until the provider revokes the refresh token.

Brama Desktop does the same in two steps, because the gateway is usually not on the machine the person logs in from: POST /v1/admin/subscription-pool/sign-in-manual returns the page and keeps the PKCE verifier in the gateway under a sign_in_id for 900 seconds; POST /v1/admin/subscription-pool/sign-in-manual/:sign_in_id takes the paste and ends in the same exchange, store and proving refresh (HTTP API). Both are brama-desktop only.

On 2026-09-12 every Claude subscription in the pool held no credential: the Skarbiec items carried a document with no grant, the only working account was signed into the harness on the operator's laptop, and every sign-in Brama offered went through Weles, which needs a login row and a browser host that account did not have. The gateway every product is told to use had nothing to answer with while the harness beside it did. The runbook entry A request answers 429 subscription_unavailable now names this command as the repair for that state.

Unreleased: the request path leaves a disowned grant alone¶

A request that ranks an agent's subscriptions no longer reads a grant the ledger already records as needs_reauthorization: the sweep left such a grant alone until a sign-in replaced it, and the request path now does the same, reporting it as awaiting_sign_in instead of paying for a router child process, a broker redemption and a refused refresh on every call. On charless-mac-mini the codex account, a document with no refresh token, was refused several times a minute for days while callers waited. A credential the vault refuses outright is remembered for sixty seconds, the window a failed model discovery already had.

Two events attribute the time a request spends before the provider answers: credential_obtained (resource, path, elapsed_ms) once per managed credential, and subscription_models_discovered (subscriptions, read, awaiting_sign_in, failed, elapsed_ms) once per ranked request. The runbook entry A request is slow before the provider answers reads them.

Unreleased: an alias resolves to exactly one route¶

An alias now names one destination and nothing else. When that route refuses, the refusal is what the caller receives: no second route is attempted, so the answer an operator reads is the answer the route gave. The request deadline is the deadline of that one attempt and is not multiplied by a number of routes.

The route registry document carries exactly three known top-level fields: schema_version, whose value is the number one, deployments, and routes, which maps an alias to its single destination. Any other top-level field is refused by the deserializer, so a document that carries one is rejected whole rather than partly read.

PUT /v1/admin/routes takes exactly the two fields below and DELETE /v1/admin/routes takes {"alias"}; both answer {"ok":true,"routes":<document> } with the committed document.

{"alias": "wisent-backend", "primary": "codex/gpt-5.3-codex-spark"}

GET /v1/aliases returns rows of {"alias", "state", "route", "reason", "required", "authorized"}, and the four alias states are unchanged: serving, no_route, capability_absent and routes_file_invalid. A completion that names a declared alias which cannot serve is 503 alias_unserviceable carrying details.state and details.route; an unknown alias is 404 whose details also carry state and route. brama aliases prints alias, state and route, and brama adopt reviews one route per alias.

brama routes migrate is new and is how an existing registry file reaches this shape without hand editing. It reads the configured document, keeps only the known top-level fields, validates the result, and commits it with the same atomic owner-only replacement every other registry write uses. It is idempotent and prints the resulting document, so a second run reports the same document the first run committed.

Unreleased: subscription plan usage replaces four invocations¶

One sweep and one ledger were asked for four ways — POST /v1/subscription-usage/:agent_id, POST /v1/account/subscription-usage, POST /v1/admin/subscription-usage/:agent_id and POST /v1/admin/subscription-pool/usage — and every one of them read the same usage ledger and the same provider reports. One capability answers it now: POST /v1/plan-usage, scoped by the identity the caller proved through the same resolver the subscription pool uses. All four were deleted in the same change: their routes, their handlers, the Brama Desktop calls that reached them, and their paragraphs on this site.

The answer is the pool's document with every reading brought current, so a row means the same thing whichever capability produced it. A provider that answered sets limits and usage_source: "provider"; a provider that refused keeps its last reading, marks it stale, and records the refusal in errors in the provider's own words; a provider with no supported free report is recorded as exactly that. None of the three reads as a plan reported unused. A request body is refused with plan usage takes no request fields; the answer follows from the proven identity, and an inventory Brama could not read stops the provider reads rather than asking about accounts nobody confirmed.

A model-scoped bearer may now reach the capability, which every workload identity the authority resolves is: none of the four routes it replaced was reachable by one, so the single audience that signs its own requests could not read its own plan usage over any of them. brama subscriptions --refresh-usage and Brama Desktop's Refresh usage both read this capability. tests/usage drives it over real HTTP against an isolated vault, an isolated Wisent Identity authority and an isolated endpoint answering the providers' own usage reports.

Unreleased: the subscription pool replaces eleven invocations¶

Which subscriptions exist and who owns them was asked eleven ways — brama subscriptions list; GET, POST and DELETE /v1/subscriptions/:agent_id; GET and POST /v1/account/subscriptions; DELETE /v1/account/subscriptions/:subscription_id; GET and POST /v1/admin/subscriptions/:agent_id; DELETE /v1/admin/subscriptions/:agent_id/:subscription_id; and GET /v1/admin/subscription-pool — and every one of them answered it from the same vault declaration. One capability answers it now: GET and POST /v1/subscription-pool, scoped by the identity the caller proved, plus brama subscriptions as a leaf command. All eleven were deleted in the same change: their routes, their handlers, their tests, the Brama Desktop calls that reached them, and their paragraphs on this site. brama subscriptions list no longer parses.

The pool document is one shape for every audience — {"ok", "observed_at_ms", "scope", "errors", "subscriptions"} — so the per-audience providers key and the agentId key are gone, and the row key subscription_id is now id, which every row already carried. scope is deployment or the agent id the answer was narrowed to. A write names an owner only from the deployment scope; an agent or account holder that sends agent_id is refused with agent_id is derived from the proven identity and must not be sent, and a deployment-scoped write that omits it is refused too. Retiring a subscription the caller does not own is 404 subscription not found even when the deployment holds it.

BRAMA_WISENT_AUTH_URL now selects the Wisent Identity origin, and an unset variable means canonical Wisent Supabase. The anon key was already deployment-configurable while the origin it was presented to was compiled in, which left the human half of every identity decision unprovable anywhere except against the production project; the account holder's scope is now driven end to end in tests/pool.

The measured command surface is 42 leaf invocations in 6 groups at 15c27474b3a870e1a399697068e2b96f4e72d8dd, down from 50 in 7 (command surface).

Unreleased: the backend alias is the client's name¶

The Wisent App backend's chat alias is wisent-backend. It was wisent-backend/chat/primary beside a rank-suffixed twin, which spelled in the alias name the same rank that the registry's own per-alias column of spare destinations then carried; that column is removed by the current contract, under which an alias carries exactly one route. The name then became wisent-backend/chat, which spelled a shape POST /v1/chat/completions already names. The alias now carries only who is asking. wisent-backend/embeddings and wisent-backend/moderation keep their purpose segment for one stated reason: each needs a route of its own and the registry is keyed by alias name alone.

Unreleased: subscription usage and failure reporting¶

brama subscriptions list --refresh-usage and Brama Desktop's Refresh usage share native free provider reports, bounded credential access and OAuth renewal. Account rows retain their last readings, reset and observation times, independent usage_check results and complete stored failure causes. Discovery, storage, malformed replies and partial refresh failures are all reported as themselves rather than as a healthy empty pool. An integration whose provider publishes no free report is recorded as unmeasured, which is not the same row as a plan measured at zero.

Desktop exposes the same account-specific errors, retained stale windows and explicit Weles/Stado Sign in action. A missing measurement time is reported as unknown. Refresh operations may wait longer than ordinary reads so that a provider or credential refusal is reported by Brama itself rather than by the caller's own transport. No OMP integration is used.

Signing an account in is the gateway's own work. Until 2026-09-09 the whole escalation sat behind BRAMA_CREDENTIAL_AUTOMATIC_SIGN_IN=1, which no host set, so a credential a provider had disowned waited for someone to run a command; that variable is gone and the sweep asks Weles by itself. A stored document that is not a credential is no longer read as a healthy grant either: it has no expiry, the sweep called it NotDue forever, and it is now recorded as needing a sign-in and handed to Weles. Everything that can stop that loop is named per account — automatic_sign_in on every pool row, automatic_sign_in.blocked in the readiness answer, and one of eight blocked_by words listed in the credentials runbook — including a gateway running on a host the registry does not place one on.

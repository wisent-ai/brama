Brama HTTP API reference

Administration and operations¶

The /v1/admin/* family is how the console changes this deployment: the route registry, provider credentials, configuration adoption and the two deliberate actions against a named subscription. Alongside them sit the three paths an operator watches: /health, /readyz and /stats.

Who the admin family answers¶

Every /v1/admin/* path answers only a brama-desktop identity carrying no model allowlist; every other caller receives 403 forbidden (captured). Responses carry identifiers, usage and status only: a subscription credential is write-only and is never part of an answer, on any path, including an error path.

GET /v1/admin/snapshot¶

Routes and providers as this process currently holds them. Captured keys: schemaVersion, whose value is the number one; automaticRollback, which is true; boundaries ({"credentials":"skarbiec","releases":"stado","routing":"brama"}); providers[] in the same shape /stats reports; and routes, the registry document as read from the configured file. When that file will not read, the answer is 503 route registry unavailable.

The registry document under routes carries exactly three known top-level fields — the schema version, deployments and routes — and routes maps each alias to its single destination:

{"deployments":[],
 "routes":{"weles":"best","ox-alpha":"openrouter/stealth/ox-alpha"}}

The document also carries schema_version, whose value is the number one. Any top-level field beyond those three is refused by the deserializer and the whole document is rejected, so a file written for an earlier shape is refused rather than read in part. That refusal is what puts every alias into routes_file_invalid. brama routes migrate reads the configured document, keeps the known fields, validates the result and commits it with the same atomic owner-only replacement the writes below use; it is idempotent and prints the document it committed.

The route registry¶

PUT /v1/admin/routes takes exactly {"alias", "primary"}: the alias, and the one route it resolves to. An unknown field is refused with the deserializer's own sentence (captured), so a body carrying anything else — including a list of further routes — does not write. Refusals:

  • 409 runtime route registry is not configured (captured) when no registry file is in effect, because there is nothing to write into;
  • 400 unknown route alias for a name this gateway does not accept as an alias;
  • a 400 route-validation refusal when the stated route is unsupported, duplicates the destination the alias already holds, or is unavailable on this deployment;
  • 409 route update was rejected when validation of the resulting document fails.

DELETE /v1/admin/routes takes exactly {"alias"} and removes that alias from the document. It answers 400 invalid route alias for a malformed name, 409 required route aliases cannot be deleted for an alias in the compiled-in contract, 404 route alias not found for one the document does not carry, and 409 route deletion was rejected when the resulting document does not validate.

Both answer {"ok": true, "routes": <document>}, the whole registry document as committed, so the caller reads the new state rather than assuming it. The write is validated first and then committed by atomic owner-only replacement: either the file is the new document or it is the old one. Nothing partial is left on disk, and a rejected write leaves the file exactly as it was.

What the resulting states look like from the client side is GET /v1/aliases.

Configuration adoption¶

Two paths take a whole configuration document and merge the aliases an operator picks out of it. Both work on the registry shape above, so an alias adopted from a source document arrives with one destination.

POST /v1/admin/configuration-adoption/preview takes exactly {"document":"<schema-1 JSON>","source_name":"<display name>","agent_id":"wisent-app"}, where agent_id is wisent-app when the request omits it. It validates the complete source and the current destination, reads the secret-free configured acquisition and subscription identities, and returns providers, subscriptions, subscription_discovery, candidates and unreferenced_deployments. It performs no write, no credential redemption, no subscription activation and no inference.

POST /v1/admin/configuration-adoption/apply takes exactly {"document":"<schema-1 JSON>","source_name":"<display name>","agent_id":"wisent-app","selected_aliases":["<alias>"],"replace_alias_conflicts":false}. It repeats the preview validation, rejects a duplicate or unknown selection, and atomically merges only the accepted selections into the configured registry file. The answer contains the resulting secret-free routes, per-alias items, and exact imported, unchanged, conflicting and rejected counts. An existing alias keeps its route unless the request explicitly asked for replacement, and a deployment conflict is never replaced.

Both adoption paths answer 409 runtime route registry is not configured when no live registry file exists, 400 <reason> for an invalid document, identity, route, selection or destination state, and 403 forbidden for any caller other than Brama Desktop. Every error path leaves the registry file unchanged and returns no credential contents.

Provider credentials¶

/v1/admin/credentials administers the standalone provider credential store this host keeps, the one a deployment without Skarbiec redeems from.

  • GET answers {"providers": ["<provider>", ...]}, the providers a credential is stored for. Names only: no credential value is returned.
  • PUT takes {"provider", "credential"} and answers {"ok": true, "provider": "<provider>"}. A provider the build does not support is 400 provider must name a supported remote API provider, and a credential the store refuses is a 400 carrying the store's own sentence.
  • DELETE takes {"provider"} and answers {"ok": true, "provider": "<provider>"}. A provider with nothing stored is 404 provider credential not found.

When this deployment keeps no standalone store at all, the read and the delete answer 409 standalone credential store is not enabled and the write is refused with the store's own sentence as a 400. In every case the request is refused, and credentials continue to be redeemed from the authority that owns them (architecture).

Administered subscriptions¶

Four paths act on a subscription the console administers. Each one happens because the console asked for it; no timer reaches any of them.

  • POST /v1/admin/subscriptions/:agent_id/:subscription_id/probe is the one path in the product that deliberately spends plan quota: one minimal completion against one named subscription, recorded as a probe with source completion. It is refused with 409 when the subscription is inside a recorded block, and 404 subscription not found when it is otherwise absent (captured). Success is {"ok": true, "probe": {...}, "subscription": {...}}.
  • POST /v1/admin/subscription-sign-in/:agent_id/:subscription_id signs in one subscription owned by the administered agent. It requires a nonempty reason and accepts login_item and login_timeout_ms.
  • POST /v1/admin/subscription-pool/sign-in signs in the selected pooled account through Weles. It requires a nonempty reason and subscription_id, and accepts login_item and login_timeout_ms. Both sign-in paths verify current ownership, refuse a retired or mismapped account, derive the provider from the selected subscription, and return the native signed_in or failed verdict with its actual detail.
  • POST /v1/admin/subscription-pool/refresh takes {"provider", "reason"} and runs the same audited refresh as brama subscription refresh, answering the verdict with status 200 (captured: {"attempted":0,"detail":"no usable `codex` subscription is in this deployment's pool, ...","provider":"codex","result":"failed"}). The verdict is the answer; only the CLI turns a failed verdict into a non-zero exit code.

Reading the pool, rather than acting on it, is discovery and subscriptions.

GET /health¶

Liveness only, no request fields, no bearer. Captured:

{"build":{"built_at":"...","platform":"...","product":"brama",
 "source_revision":"...","version":"0.2.38"},
 "dependencies":"not_probed","status":"ok"}

It never redeems a credential, lists subscriptions or contacts a provider: it answers ok from a gateway whose every redemption is being refused (architecture). Treat it as evidence the process is running, and nothing else.

GET /readyz¶

The latest completed credential and routing check. A background sweep redeems configured provider capabilities and active subscription credentials and checks model discovery; this request returns its completed report without performing those operations again. Credential redemption waits outside the HTTP workers, so slow Skarbiec responses do not prevent the gateway answering this route.

{"build":{...},"denied":[],"operator_action_required":false,
 "providers":[{"credential":true,"provider":"openai"}],
 "ready":true,
 "reason":"every configured provider credential was obtained, every active subscription redeemed, and every vault account carries the agent tag that makes it routable",
 "routing":[],"subscriptions":[],"unredeemable":[],"unroutable":[],
 "unroutable_accounts":[]}

The status is 503 with ready: false until a check has completed or when no configured route can obtain a credential. A gateway with working routes and failed accounts reports 200 and degraded: true. Routing results appear under routing. Rows in subscriptions[] carry per-subscription redeemable and the refusal in the words of whatever refused it, and never a secret.

GET /stats¶

Bearer-protected process telemetry, with no dependency probing. Captured keys: build, configuredDirectProviders, dependencyPolicy ({"capabilityBroker":"final-use","catalog":"lazy","subscriptions":"lazy"}), limits (maxOutputTokens and requestDeadlineSeconds as this gateway is configured), models[] with per-model count, latencyMs, lastLatencyMs, tps and lastTps, perfModels, and providers[] with per-descriptor id, displayName, wireProtocol and configured. It also carries the cumulative total_requests, total_failures, total_provider_attempts, total_input_tokens, total_output_tokens and uptimeSeconds.

configured reports the declared capability or field-scoped route, not successful authentication. Neither /stats nor the admin snapshot issues credentials; use /readyz for observed redemption failures and a real completion to verify the full inference path.

Because an alias resolves to one route, total_provider_attempts counts one attempt per request that reached a provider, plus any credential rotation the gateway made before the first byte. Process telemetry is not durable billing evidence: it resets with the process.

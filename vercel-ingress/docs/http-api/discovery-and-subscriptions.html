Brama HTTP API reference

Discovery and subscriptions¶

Four paths answer what a caller may ask for and what it owns: the model catalog, the alias listing, the subscription pool and plan usage. A fifth signs one subscription in for the authenticated account. All of them require a bearer (transport and identity).

GET /v1/models¶

Public catalog metadata combined with what the caller can execute: account discovery marks the models executable by that account's stored keys, and signed agent discovery includes agent-owned subscriptions. Captured shape:

{"data":[{"id":"<provider>/<model>","object":"model","owned_by":"<provider>"}, ...]}

A declared alias the caller may name but that cannot serve is listed with available: false and an unavailable_reason; it is not omitted from the answer. The reason is a fact about this gateway's configuration, so it is shown to every caller. See an alias that cannot serve says so.

GET /v1/aliases¶

Every alias this gateway declares — the compiled-in contract plus every operator route — with the state the gateway would put it in right now and the one route it resolves to. Captured shape:

{"object":"list",
 "unserviceable":1,
 "aliases":[
  {"alias":"weles","state":"serving","route":"best",
   "reason":null,"required":true,"authorized":true},
  {"alias":"ox-alpha","state":"capability_absent",
   "route":"openrouter/stealth/ox-alpha",
   "reason":"alias `ox-alpha` routes to openrouter/stealth/ox-alpha but this gateway holds no provider credential for openrouter; issue the provider capability on this host or point the alias at a route it can reach, such as `best`",
   "required":false,"authorized":true}]}

A row is exactly {"alias", "state", "route", "reason", "required", "authorized"}. route is the single destination the registry maps the alias to, so a row states one route and never a list. state is one of serving, no_route, capability_absent or routes_file_invalid; reason is null for a serving alias and otherwise the sentence a refusal would carry; required says the alias is part of the compiled-in contract; authorized says the presenting bearer may name it. A completion naming an alias whose state is not serving is refused with 503 and code alias_unserviceable, carrying that same sentence as its message and the row's state and route in details.

The same listing on the terminal is brama aliases, which prints alias, state and route. brama routes migrate is what moves an existing registry document to the shape this listing reads.

The subscription pool¶

One read and one write on /v1/subscription-pool, for three audiences. Which subscriptions exist and who owns them was previously asked eleven ways — an agent-signed lifecycle, an account lifecycle, an administered lifecycle, a console pool listing and a CLI leaf — and each answered the same question from the same vault declaration. This capability answers it once and narrows the answer by the identity the caller proved (entitlement), which is where ownership already lives.

The scope is read off the proof, in this order:

  • a caller presenting the HMAC trio is that agent, and is held to the signature even when its bearer would also pass for something wider;
  • a verified Wisent user session is that account, whose pool is keyed on the session's own user id and never on a caller-supplied identifier;
  • a brama-desktop identity with no model allowlist is this deployment: every account it holds, whichever agent owns it, plus the accounts only the usage ledger still remembers.

Anything else is 403 forbidden; a request with no bearer at all is 401 unauthorized. A model-scoped bearer reaches this path and plan usage; together with /v1/models those are the only paths outside inference it may reach at all.

Reading the pool¶

GET answers one document for every audience: {"ok", "observed_at_ms", "scope", "errors", "subscriptions"}. scope is deployment or the agent id the answer was narrowed to, so a caller reads the narrowing instead of inferring it from the row count. Every row carries the same fields whoever asked: id, provider, status, state (live | expired | burnt | unknown), expires_at, last_redeem_error, limits, measured, block, observed_at_ms, probe, usage_check, credential (state: active | needs_reauthorization | disabled, with cause and instants), usage_source and stale. No error names an account outside the caller's narrowing. Field semantics are in concepts/subscription.

Writing the pool¶

POST takes {"action", "agent_id"?, "provider"?, "label"?, "api_key"?, "login_item"?, "subscription_id"?}, and an unknown field is refused with the deserializer's own sentence. action is bank or retire; anything else is 400 action must be "bank" or "retire".

  • agent_id names the owner and may be sent only by the deployment scope, which is the one caller whose proof is not itself an agent. Sending it as an agent or an account holder is 400 agent_id is derived from the proven identity and must not be sent; omitting it as the deployment is 400 agent_id names the agent whose pool is written and is required for a deployment-scoped write; a malformed one is 400 invalid agent id.
  • bank stores a credential on the coordinate the routes table already names for that subscription. With no subscription_id the deterministic primary slot is written; an explicit id selects another existing subscription owned by that agent, and the primary slot is overwritten only when the request names it. Refusals: 404 subscription not found for an unknown or unowned selection, 409 selected subscription belongs to a different provider, 400 provider must name a supported remote API or subscription provider, 400 api_key must contain 1..8000 characters, 400 login_item must contain 1..160 ASCII letters, digits, hyphens, underscores or dots, a document that does not reduce to a bearer (400), a mapping conflict (409) and a failed vault write (500). Success is {"subscription": {"id", "provider", "agent_id", "status": "active", "label", "login_item"}}; the credential value is never returned.
  • retire requires subscription_id (400 subscription_id is required) and answers 404 subscription not found for a target the proven owner does not own, including one the deployment holds for somebody else. Success is {"ok": true}. Retirement is a journal record that outranks whatever the last refresh concluded, never a vault deletion.

POST /v1/plan-usage¶

What every plan the caller proved it owns has left. One invocation for the same three audiences, replacing the four per-audience refreshes this page used to list — POST /v1/subscription-usage/:agent_id, POST /v1/account/subscription-usage, POST /v1/admin/subscription-usage/:agent_id and POST /v1/admin/subscription-pool/usage — each of which read this same ledger and these same reports. They are gone from the router (command surface).

The scope is read off the proof in exactly the order the pool reads it, through the same resolver. Anything else is 403 forbidden; a request with no bearer at all is 401 unauthorized. A model-scoped bearer reaches this path, which is what makes a signed workload able to read its own plans at all.

It is a POST because answering reads each provider's own usage report and records what it said. That spends no plan quota: no completion is sent and no sign-in is started. A read asked for here is taken now, unlike the timer's sweep, which reads an account only once per its own cache window (BRAMA_PLAN_USAGE_TTL_SECS); concurrent readers join one bounded read per account rather than asking a provider the same question twice in the same second, and no more than four accounts are read at a time because several accounts on one host share one source address.

The body is empty and signed empty — the answer follows from the proven identity, so a request carrying any field is 400 plan usage takes no request fields; the answer follows from the proven identity rather than answered from a signature over something the handler disregards.

Subscription usage results¶

The pool read and plan usage answer one document: ok, observed_at_ms, errors, scope and subscriptions, with every reading in the plan-usage answer brought current. A completed report can return HTTP 200 with ok: false: the body retains the successful rows and carries standard Wisent failure envelopes for the failures, so clients inspect ok rather than read success out of the HTTP status. An admission failure still uses the ordinary HTTP error body.

Three outcomes stay distinct per account.

  • A report the provider answered sets limits with each window's used_fraction, its reset and observation instants, and usage_source: "provider". Window percentages come only from valid provider metrics.
  • A report the provider refused keeps the last good reading, marks it stale, sets usage_check.ok: false, and puts the refusal in errors in the provider's own words with its status — an incomplete answer that names the account it is incomplete about. A missing measurement is never reported as zero usage.
  • A provider with no supported free report is recorded as exactly that, which is a third statement and not a failure.

Each row carries usage_check with the latest free report attempt's attempted_at_ms, ok, detail and source, kept separate from a completion probe. An inventory Brama could not read stops the reads and is reported instead, because a listing that failed says nothing about which accounts exist. A dependency timeout, an invalid response or a storage failure appears in the result naming the failed operation and the actual reason.

Sign-in is asked for explicitly¶

POST /v1/account/subscription-sign-in/:subscription_id signs in one subscription owned by the authenticated account. Neither the pool read nor plan usage ever starts this flow; it happens because a caller asked for it on this path.

The sign-in routes require a nonempty reason and accept login_item and login_timeout_ms; the pooled administrative variant additionally requires subscription_id in the body. Brama verifies current ownership, refuses a retired or mismapped account, derives the provider from the selected subscription, and invokes the existing Weles flow on the Stado-selected host. It returns the native signed_in or failed verdict with the actual detail. The two administered variants are in administration and operations.

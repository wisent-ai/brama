Brama HTTP API reference

Transport and identity¶

Two guards stand in front of every path in the route table: the transport guard, which every route passes through including /health, and the identity guard, which every route except /health and /readyz passes through. This page is what both of them check, what a caller sends to satisfy them, and the shape of the answer when one of them refuses.

Accepted transports¶

A request is accepted only when its peer is loopback, the address the gateway itself bound, a peer named in BRAMA_ENCRYPTED_PEER_IPS (a mesh hop that is already encrypted), or a proxy named in BRAMA_TRUSTED_PROXY_IPS whose Forwarded/X-Forwarded-Proto headers state https. Anything else receives status 426 with this body (captured):

{"error":{"attempts":0,"code":"secure_transport_required",
 "message":"HTTPS is required except for direct loopback requests",
 "retryable":false,"type":"transport_error"}}

Forwarded headers presented by a peer that is not in BRAMA_TRUSTED_PROXY_IPS are never read as evidence of the scheme. The guard runs before the handler, so a refused request never reaches a provider and never touches the vault.

Bearers¶

Protected routes take exactly one Authorization: Bearer <token> value. The token is compared in constant time against the identities in BRAMA_MODEL_ROUTER_CLIENT_IDENTITIES. A bearer that is not in that table is resolved against Skarbiec, the authority that issued it, and, for account-scoped routes, against Wisent Identity. When an authority cannot answer, the request is refused rather than admitted, and a resolved verdict is cached for five seconds so that a revocation takes effect without restarting the gateway.

A model-scoped bearer — one carrying allowed_models — may reach the five inference paths, /v1/models, the subscription pool and plan usage; the allowlist itself is then enforced per request, further in. Every other path, including /v1/aliases and the whole admin family, answers 403 forbidden. A request with no bearer at all on a protected path is 401 unauthorized.

The organization header¶

A human bearer is not yet an identity: it names a user, and a user may belong to several organizations. The request states which one with a single X-Wisent-Organization-ID header carrying a UUID, and Brama asks Wisent Identity to authorize that user for that organization with that same bearer. The identity it caches is keyed on the token digest and the organization id, so a bearer authorized for one organization is not an identity in another.

A missing header, more than one of them, a value that is not a UUID, or an organization the bearer is not authorized for is refused. The first three answer 400 a valid X-Wisent-Organization-ID header is required; an unauthorized pairing answers 403 forbidden. Workload bearers carry no organization context and send no such header.

Agent signatures¶

An agent-scoped operation additionally signs the exact raw request body with the HMAC trio described in concepts/entitlement. The signature is over the bytes as sent, so a proxy that reformats the body invalidates it. A route that requires the trio and does not receive it names the header that is missing, for example 401 {"message":"missing x-agent-id header"} (captured on model:"best").

Where a request field would restate an identity the signature already proves, sending it is refused instead of being ignored — see discovery and subscriptions for the two cases, agent_id on a pool write and any field at all on plan usage.

Shared request limits¶

Three limits hold for every request the gateway admits.

  • The requested output size is bounded by the gateway's own maximum, which GET /stats reports as limits.maxOutputTokens. An inference request asking for more is refused with the sentence in inference.
  • The request deadline, reported as limits.requestDeadlineSeconds, is the deadline of the one attempt the request makes. Because an alias resolves to exactly one route, there is no number of routes for it to be multiplied by.
  • Unknown request fields are refused with the deserializer's own sentence, naming the field it did not expect and listing the fields it did. The bodies on every page in this family are therefore exhaustive.

The refusal envelope¶

Every refusal on every route uses one envelope, whose fields — type, code, message, retryable and attempts — are documented in errors. Two cases are worth stating here because they are the shape of the route contract.

A request naming an alias this gateway declares, whose state is anything other than serving, is refused with 503 and code alias_unserviceable. Its details carry state, one of no_route, capability_absent or routes_file_invalid, and route, the single destination the registry maps that alias to. The message is the same sentence GET /v1/aliases gives as the row's reason, so the refusal and the listing agree.

A request naming an alias this gateway does not declare is 404, and its details carry the same two fields, with state reporting that there is no route for that name. In both cases the refusal is what the caller receives: the resolved route is attempted once, and its answer, including its refusal, is the answer to the request.

{"error":{"code":"alias_unserviceable","type":"invalid_request_error",
 "message":"alias `ox-alpha` routes to openrouter/stealth/ox-alpha but this gateway holds no provider credential for openrouter",
 "retryable":false,"attempts":0,
 "details":{"state":"capability_absent","route":"openrouter/stealth/ox-alpha"}}}

Repairing the state an alias is in is an operator action, not a client one: point the alias at a route this gateway can reach, or issue the provider capability here. The registry write is PUT /v1/admin/routes, and brama routes migrate brings an existing registry document to the current shape.

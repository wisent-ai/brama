Brama runbook: credential authorization and the subscription pool

Credentials and subscriptions¶

Six symptoms that all end at one question: which credential was supposed to pay for this request, and what refused it? Read the refusal sentence first — each one names a different repair, and none of them is repaired by waiting. The error vocabulary is in errors; the rest of the runbook is at runbook.

A request answers 503 credential_unauthorized¶

The dispatch sentence behind it is usually direct '<provider>' credential is unavailable — no capability, read grant, or standalone credential could produce a secret for that provider at final use. It is retryable: false on purpose: waiting does not reach an authorization that does not match, and the refusal is what the caller receives. Check, in order: /readyz (denied[]), the launcher's provisioned trust material (bin/provision-skarbiec-trust was run once on this installation), and whether the alias's route names a provider this host was ever granted (alias_provider_capability_absent in the log at startup: "no provider capability was issued for this route; the alias will not serve").

An alias in that condition reports state capability_absent in brama aliases and in GET /v1/aliases, and a completion naming it answers 503 alias_unserviceable with the state and the route in details.

A request answers 429 subscription_unavailable¶

The dispatch sentences, from narrowest to widest (concepts/entitlement):

  • no active '<provider>' credential for agent — the signed agent owns no eligible credential for the provider the route names.
  • no active stateless provider models for signed agent — a selector found no candidate at all.
  • no working subscription model for signed agent — the selector walked its whole bounded candidate list; the body's attempts counts the provider calls actually paid for.
  • all bounded '<provider>' credentials unavailable for agent — every bounded credential was tried or is inside a recorded block.

First command: brama subscriptions. 0 of 0 subscription credentials are live is the whole diagnosis — sign an account in. Rows present but refused carry last_redeem_error in the words of whatever refused (credential cause first, then a block still in force, then the newest failed check; a lapsed block is deliberately not reported). For claude-code, when the account that works is one a person can log into but Weles cannot, the sign-in is done by hand: the person logs in with their own browser and pastes the code back. Where Brama runs, on a terminal:

$ brama subscription sign-in-manual claude-code --subscription-id <id> --reason "<why>"

It prints the page to open, waits for the pasted code, stores the grant and proves it with a refresh; exit 0 with result: signed_in is the proof (cli). From another machine, Brama Desktop’s Sign in by hand on the selected account does the same two steps against the gateway; result: signed_in on the screen is the proof.

A subscription reads burnt¶

burnt covers both recorded dead states — a grant the provider disowned and a subscription somebody retired — and last_redeem_error says which. A definitive provider refusal (invalid_grant, invalid_token, revoked, unauthorized_client, or an unexplained 401/403) is recorded as credential.state: needs_reauthorization with the provider's own sentence as cause, and the credential is left untouched until a sign-in replaces it — the refresh timer will not resurrect it, and a 30-minute block holds the dispatcher off it. Repair: on the host Weles runs on, one command does the whole sequence — the sign-in through Weles and the refresh that proves it:

$ brama subscription sign-in <provider> --reason "<why>"

Exit 0 with result: signed_in is the proof (cli). Where Weles is not reachable, sign the subscription in by hand — for claude-code with brama subscription sign-in-manual, which runs the proving refresh itself; otherwise through Desktop or a donation, then:

$ brama subscription refresh <provider> --reason "<why>"

Exit 0 with result: refreshed is the proof; result: failed quotes each refusal in the provider's own words. A retirement outranks everything: a retired subscription is never refreshed.

subscription refresh reports it attempted nothing¶

The command exits with an attempt count of zero and this detail:

detail: no usable `<provider>` subscription is in this deployment's pool, so
no credential source is configured to refresh: one has to be signed in and
stored in the vault before this command has anything to act on

Not a fault in the refresher — the pool is empty for that provider. The same sentence answers a provider with no OAuth path. Sign an account in first; the walkthrough shows the full sequence (walkthrough-subscriptions).

An account vanished from every listing but keeps paying¶

The tag-loss case: discovery finds an account by its brama:agent: tag, so an item that loses it stops existing for every caller and every screen while its credential stays valid. Nothing that lists subscriptions can say so — the listing is the thing that lost it. The one reporter is /readyz: unroutable_accounts[] names the item id, provider, and coordinate (items stripped bare are recognised by the provider:<provider>:<id> coordinate alone). Repair in the vault: restore brama:subscription, brama:agent:<agent>, brama:provider:<provider>, brama:id:<id>.

A provider refuses its own credential¶

A direct route whose provider answers 401 returns 502 provider_failure with the provider's sentence behind the kind prefix; the body's attempts field counts the single provider call that was made:

{"error":{"code":"provider_failure",
 "message":"provider_authentication: Incorrect API key provided: ...", ...}}

Distinguish it from 503 credential_unauthorized: the 502 means Skarbiec (or the standalone map) produced a credential and the provider rejected it — the repair is at the provider account, not the authorization chain. Because the alias names one route, that provider's answer is the answer the caller reads. A provider 429 surfaces as 429 provider_rate_limited with retryable: true; a recorded block (default 15 minutes, provider-stated resets capped at 7 days) then marks that account unusable until the block lapses, and requests that need it are refused in the meantime.

A request is slow before the provider answers¶

Two log lines say where the time between routing_decision and routing_complete went. credential_obtained is written once per managed credential, with resource, path (configured, issued or read-grant — which step of the cascade answered) and elapsed_ms: the whole cascade, which is a child process to the entitlements router and a broker redemption. subscription_models_discovered is written once per request that ranks an agent's subscriptions, with subscriptions, read (credentials read from the vault this time), awaiting_sign_in (left alone because the ledger says a sign-in is owed), failed and elapsed_ms. A request that spent nine seconds with elapsed_ms small on both lines spent them at the provider.

The request path trusts the ledger the way the refresh sweep does. A grant the provider disowned — credential.state: needs_reauthorization, with the provider's sentence as cause — is not read from the vault and not refreshed again until a sign-in replaces it; it appears in subscription_models_discovered as awaiting_sign_in. Until 2026-09-10 every request that ranked the account paid for that read and for the refusal — on charless-mac-mini, brama-sub-wisent-app-codex-primary, a document with no refresh token, was refused several times a minute for days and every caller waited on it. A credential the vault refuses outright is remembered for sixty seconds, the same window a failed model discovery is.

Why an account cannot be signed in¶

Brama resolves a subscription from Skarbiec and delegates authentication to Weles. Weles reads the matching login material from Skarbiec and performs OAuth on the Stado-selected host, without provider CLIs or copied local sessions. No second account catalogue or manually added login tag is required.

The pool's automatic_sign_in.last_attempt records the outcome. For a failure, inspect failure.code, failure.stage, failure.http_status, failure.run_id and source_revision. The detail is the service's actual response, not an explanation inferred from a missing configuration field. Readiness and Desktop show this same observation.

CodeObserved operation
subscription_identity_missingThe Skarbiec subscription has neither a principal nor an unambiguous reference to a login item.
skarbiec_login_missingNo Skarbiec login item matches the principal the subscription declares.
skarbiec_login_ambiguousSeveral login items match; the response lists their identifiers instead of selecting an unrelated account.
login_identity_changed, skarbiec_identity_changedThe account changed between resolution and credential use; no grant for the old identity is accepted.
weles_unreachableThe request to Weles failed; the detail includes the operation, address and transport error.
oauth_provider_refused, provider_challenge_refusedThe provider refused the OAuth or login operation. Its response and the Weles run are retained.
credential_persist_refused, persisted_credential_refresh_failedThe login did not yield a usable persisted subscription credential; it is not reported as repaired.
authentication_outcome_unclassifiedAn older recorded failure lacks structured operation evidence. Its original detail remains visible; it is not proof that a provider rejected the account.
not_placed_hostStado reported that this gateway runs on a different host than the declared placement.

The repeat check uses the resolved Skarbiec account-data revision and the actual attempt result. It retains the refusal for unchanged, non-retryable provider challenges rather than repeatedly submitting passwords or codes. An identity-resolution failure is not recorded as a completed browser login.

An account nobody signs in — an API key, or a retired subscription — reports applies: false and no word at all, so a healthy account is never shown as awaiting something. Weles signs in claude-code, codex and kimi.

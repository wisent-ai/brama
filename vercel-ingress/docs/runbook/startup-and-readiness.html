Brama runbook: startup, reachability and readiness

Startup and readiness¶

Five symptoms that appear before any model request succeeds: the public endpoint is not published, the process refuses to start, /health says ok while nothing serves, /readyz answers 503, or a request from another machine is refused at the transport. Each entry quotes the sentence the product actually prints and names the repair. The error vocabulary itself is in errors; the rest of the runbook is at runbook.

The public endpoint fails while CI waits for a key¶

The funnel-keepalive workflow publishes Brama's origin from Stado's service directory every five minutes. Its checked-in .github/workflows/funnel-keepalive.yml step changes only the root path on HTTPS port 443; it preserves the Stado object and integration paths on the same port. A queued workflow has not published anything, even when the runner is online.

For an empty HTTP 502 from the public endpoint, compare the declared origin with the current forwarding rule and inspect the publisher's job:

stado service directory bind brama --target charless-mac-mini --json
stado host exec charless-mac-mini -- tailscale serve status --json
gh run list --repo wisent-ai/brama --workflow funnel-keepalive.yml

If a checkout waits in git-credential-osxkeychain, do not approve a system dialog or restart the runner. Brama's jobs on the release runner create an empty, job-local Git configuration before checkout, ignore system Git configuration, and disable terminal and askpass prompts. Checkout uses its GitHub token; private dependency authorization writes only to that job's Git configuration, not the host's shared configuration. A missing credential makes the job fail visibly instead of opening a consent window. Jobs started from an older revision retain their old settings; cancel a stuck old run before scheduling the corrected publisher, rather than rerunning the old revision.

A completed publication proves the forwarding rule, not model inference. Confirm the original authenticated request against Brama before treating the caller as repaired.

brama serve refuses to start¶

The sentence, verbatim (exit 1):

Server error: BRAMA_MODEL_ALIASES is required and is assembled by
src/release/bin/start-with-skarbiec from the sealed policy directory. Starting the
binary directly cannot obtain it: launch the gateway through that launcher, or
export the variable yourself. Restarting an unlaunched process will not
repair this.

The refusal names its own repair: managed configuration is generated by the launcher, and restarting the same bare invocation cannot change the answer. Start through src/release/bin/start-with-skarbiec; a standalone desktop deployment instead passes --local-credentials-stdin (configuration). Other startup refusals in the same class — duplicate client tokens, malformed identities, an alias route with * or stray whitespace — also stop the process before it binds; the log names the offending entry.

An alias declares exactly one route, so a startup refusal about a route is a statement about that one destination. If the registry document itself is the thing being refused, repair it with brama routes migrate (cli/routes/migrate) and see routes and ledger.

/health is ok but nothing works¶

That is /health doing its job, not a contradiction: its body says "dependencies": "not_probed", and it answers ok from a gateway whose every credential redemption is being refused. The only readiness evidence is /readyz (architecture). Point deploy checks and uptime monitors at /readyz; treat a monitor on /health as a monitor of the process, nothing more.

/readyz answers 503¶

reason is one of five sentences (src/core/server.rs:2343-2355), each naming a different repair:

reason Meaning Check
no provider capability is configured zero direct providers — the gateway can route nothing on its own account launcher policy: required_provider_capabilities and the authority-owned capability routes table
a configured provider credential could not be obtained; the authorization chain is broken, not busy a capability or read grant refused just now denied[] names the providers; check broker socket, workload registry, proof key (concepts/capability)
an active subscription's credential did not redeem just now, so the next request that needs it will be refused whatever the catalogue lists a subscription is listed but its credential does not redeem unredeemable[], then brama subscriptions for the refusal sentence
the vault holds a subscription account whose item carries no agent tag: it is unroutable, and no subscription listing can report it an account lost its brama:agent: tag; the credential still works and nothing can route to it unroutable_accounts[] names item and coordinate; restore the tag in the vault
every credential was obtained, and at least one active subscription contributes no model: it cannot be routed to a redeemable account whose provider offers it no discoverable model unroutable[]; check provider model discovery and the account's plan

Waiting repairs none of these — every 503 here is an authorization or inventory statement, not load. The three subscription-shaped rows are worked through in credentials and subscriptions.

Requests from another machine answer 426¶

{"error":{"code":"secure_transport_required",
 "message":"HTTPS is required except for direct loopback requests", ...}}

The transport guard accepts loopback, the gateway's own bound address, peers in BRAMA_ENCRYPTED_PEER_IPS, and proxies in BRAMA_TRUSTED_PROXY_IPS whose forwarded headers state https — nothing else, and forwarded headers from an unlisted peer are never trusted (a forged X-Forwarded-Proto: https changes nothing; captured). Repair: front the gateway with the approved TLS terminator and list that terminator's peer IP, or call over the mesh hop that is already encrypted.
